# 用量历史统一实施方案（2026-11-27）

**状态：阶段一、二已实现，待预览版 CI 与发布验收；阶段三待单独评审。** 基线为 `v1.11.0-preview.1`（`614c5dd`）。本文件整合[原改进方案](usage-history-display-mode-select-plan.md)与 2026-11-27 的代码审核，作为实施和验收依据。原方案中的本机文件数量、读数数量和容量测算是 2026-11-26 的快照，不能当作当前状态或全体用户的数据。

## 产品决定与范围

1. 折线只放在独立的“用量历史”窗口。设置页不内嵌图表；把“显示方式”与“打开用量历史”入口放在同一个“用量历史”设置区，并用一句说明指向独立窗口。移除只有一个下拉框、容易被误认为空图的“时间折线”区块。
2. 两处“显示方式”使用同一个 `historyShowUsed` 设置，选项统一为“剩余额度”和“已用额度”；默认仍为“剩余额度”。每日消耗、额度窗口及保护阈值含义不因控件替换而改变。
3. 历史保留期限提供“三个月”“六个月”“一年”“全部保留”四项。**现有和新用户默认全部保留**；旧配置没有该字段时也迁移为“全部保留”。停止记录只停止新增读数，不立即清除已有文件；已有文件仍受所选保留期限约束。彻底删除继续使用独立的“清除历史”确认操作。
4. 历史窗口维持现有 24 小时、7 天、30 天、90 天四个查看选项；本次不增加日期范围、翻页或“全部”查看功能。超过当前 90 天查看范围但仍在保留期限内的正式读数继续存放在本地历史文件中，界面暂不展示。
5. 预测状态继续作为有界派生状态保存，历史 JSONL 继续记录可查看的稀疏真实读数。二者共用同一次来源读取，不增加额度请求。预测旧状态中的插值跨越事件不作为精确历史导入，也不进入每日消耗或额度窗口统计。

## 阶段一：显示方式与设置页

**改动。** 在 `HistoryView.tsx` 中以带可见 `<label>` 的原生 `<select>` 替换两个模式按钮。值由 `settings.historyShowUsed` 控制；只有值发生变化时才调用一次 `onPatchSettings`，不维护第二份本地选择状态。无保存回调时沿用当前行为，不显示可编辑控件。保留标题、提示、曲线、纵轴、保护阈值、悬停及键盘读数随模式变化的现有行为。

在 `SettingsView.tsx` 中将现有下拉框移入“用量历史”的记录设置区，与“打开用量历史”入口相邻；添加简短说明，指出折线位于独立窗口。两处共用相同的标签和选项翻译。更新 `i18n.ts` 中的英语、简体中文、繁体中文，以及 `locales/ru-RU.json` 的俄语；只改相关文案。

**验收。** 两处读取同一设置；从任一处切换，保存成功后另一处及折线同步。保存失败时由现有设置回滚流程恢复。键盘和屏幕阅读器能识别标签、当前值和选项。无回调的历史窗口不出现可编辑控件。更新 `HistoryView.test.tsx`、`SettingsView.test.tsx` 的交互断言，运行前端测试与构建，并查看浅色、深色主题和设置窗口最小宽度 760 像素下的布局。该阶段不改 Rust 历史格式、存储和查询。

## 阶段二：保留期限与迁移

### 设置契约和启动顺序

- 在 Rust `OverlaySettings`、严格校验的 `SettingsPatch`、前端类型及默认值中加入一个枚举式保留期限（例如 `3m | 6m | 1y | all`），而非多个布尔开关。旧配置缺少字段时迁移为 `all`；未知值不得触发清理，应按“全部保留”处理并报告配置问题。翻译、设置页说明和保存失败回滚与现有设置机制一致。
- 应用创建 `Store` 时就传入已经读取的保留期限；任何 `append`、`records`、系列列表或自动清理开始前，存储层必须知道有效期限。设置改变时，在同一存储锁下更新期限、缓存和清理状态，避免旧的 90 天常量在默认“全部保留”时误删文件。退出、重启后仍按已保存的值生效。
- 旧版本**已经删除**的文件无法恢复。升级后默认“全部保留”须保护当时尚存在的正式历史文件，包括超过 90 天的文件；不能先运行旧清理逻辑再迁移设置。界面说明默认保留只对现存及今后记录生效，不承诺补齐未记录或已删除的数据。验收应覆盖应用停用数月后升级及再次启动。

### 缩短期限与清理

- 从较长的期限切到较短的期限前，先列出将删除的日期范围、文件或读数估计及可用空间变化，要求明确确认；取消不得改变设置或删除数据。选择更长的期限不删除文件。界面显示所有来源的历史文件总占用、最早与最新正式读数时间，并标注统计时间。
- 定义三个月、六个月和一年为从当前 UTC 时间分别向前推 3、6、12 个日历月；遇到目标月份没有对应日期时取该月最后一天。清理既删除完全过期的整月文件，也原子重写跨越截止点的边界月份，避免选定期限外的读数继续留在磁盘。临时文件、替换和异常恢复须保证原文件或完整新文件至少有一份可读；不得在改写失败时宣称清理成功。
- 保存设置与文件清理无法构成单个磁盘事务。实现须明确顺序和失败状态：先持久化目标期限，再执行可重试清理；清理失败时保留已保存的期限、显示“清理未完成”及错误，并在下次启动重试。任何已删除文件都不因设置保存回滚而被声称恢复。手动“清除历史”继续独立运作。

**验收。** 覆盖旧配置迁移为“全部保留”、三个月/六个月/一年/全部保留四种设置、跨月和跨年、应用停用后升级、重启、关闭记录、清理确认及取消、边界月份、部分写盘失败和清理重试。测试应检查磁盘文件与现有 90 天查询结果，而不只检查设置值；默认“全部保留”时，超过 90 天的现存文件仍在磁盘，历史窗口的四个查看选项不变。对写盘失败的演练使用隔离的临时目录，不能触碰用户真实历史。

**存储边界。** 磁盘清理按所选保留期限执行；历史窗口和查询命令仍最多查看最近 90 天。`Store` 的内存缓存继续只保存查看所需的近期读数，不能因默认“全部保留”而加载所有年份。超大月文件或损坏行不能被静默当成“没有历史”；应报告读取问题。本阶段不增加查询接口、历史窗口控件或长期范围统计。

## 阶段三：旧预测状态的可恢复性评估（独立立项门槛）

先做**只读扫描和预览**：逐文件列出来源、可核验账号、真实 `lastObservedPercent` / `lastObservedAt` 点、插值跨越点、重置/分段边界、与正式 JSONL 的重叠和缺口。实施导入前备份原预测状态与历史文件，不改预测器原状态。不同来源或身份无法可靠匹配的点不导入。

若预览显示确有价值，再单独设计数据来源标记及存储：真实观察与“根据预测状态估算”的点必须能在磁盘格式、Rust 查询和前端图例中区分。现有 `Record` 没有这个字段，不能直接把估算点写入正式 JSONL 后交给现有 `query::daily`、额度窗口和触顶统计。导入须可重复执行、去重且可回滚；精确统计只消费正式真实读数。评审通过这些契约和样本验收后，才安排导入实现。该阶段不阻塞前两阶段交付。

## 提交与交付顺序

1. 阶段一作为独立界面里程碑提交；前端测试、构建和布局检查通过后交付。
2. 阶段二先落默认“全部保留”的设置迁移与安全清理，再开放四个期限选项；存储测试通过后交付。发布前核对默认值、保留说明及现有查看范围不变。
3. 阶段三仅在可恢复性预览和来源标记设计获得单独评审后实施。各阶段只提交本阶段改动，并遵守仓库的 CI、发布和 Git 规则。

本方案不承诺恢复旧版本未记录、已清除或已被 90 天规则删除的历史。正式实现前需以当前代码和实际测试结果重新核对所有性能与容量估计。
