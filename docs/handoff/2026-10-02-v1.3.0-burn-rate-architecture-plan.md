# Codex Usage Overlay v1.3.0 — Burn Rate + Architecture Optimization Plan

**Date:** 2026-10-02  
**Project:** `D:\OneDrive\AiPrograms\codex tools\codex-usage-overlay`  
**Baseline:** v1.2.1 / `main` / `751a4f9`

**Plan revision:** design-reviewed after commit `0209657`; this revision closes estimator/reset/startup/persistence edge cases before production implementation.

## 1. Goal

Add account-level quota burn-rate estimates to the existing 5-hour and weekly quota display while preserving the current compact overlay layout and all existing v1.2.1 behavior.

Primary new metrics:

- 5-hour burn rate: percentage points of the 5-hour quota consumed per hour.
- Weekly burn rate: percentage points of the weekly quota consumed per hour.

The feature deliberately replaces the need for token/s as the primary practical speed metric. It measures how quickly the account allowance is actually being consumed across all simultaneous Codex sessions.

## 2. Current architecture audit

The existing project already has the right overall technology stack and should **not** be rewritten.

Current stack:

- Tauri 2
- Rust backend
- React / TypeScript frontend
- WPF/C# migration is **not** recommended for this repository.

Current usage path:

```text
background polling
  -> CodexClient::fetch_usage()
  -> spawn codex app-server --stdio
  -> initialize
  -> account/rateLimits/read
  -> parse CodexUsage
  -> process_usage_success()
  -> usage_updated event
  -> React OverlayView
```

The account-level `account/rateLimits/read` source should be retained. It already aggregates all concurrent Codex sessions and avoids reading `auth.json`, scraping the UI, or merging session logs.

## 3. Confirmed constraints

Current local inspection of `account/rateLimits/read` shows `primary.usedPercent` and `secondary.usedPercent` arriving as integer-valued JSON numbers. No higher-precision production field was found in the current app-server response or local rate-limit records.

That observation is a property of the **current server output**, not a protocol guarantee. The existing parser already reads `usedPercent` as `f64`; v1.3.0 must preserve that raw numeric precision internally even though the current values happen to be integers.

Therefore v1.3.0 must:

- use observed integer quota crossings as the estimator evidence available today;
- derive rate from crossing timing rather than invent decimal usage precision;
- retain raw `usedPercent` internally as `f64`, so future decimal server values are not discarded;
- keep the existing account API;
- retain `windowDurationMins`, `resetsAt`, and the returned account identity where available for validation/cycle handling;
- avoid HTTP/WebSocket proxying, token-stream interception, session-log aggregation, or custom Codex builds.

The default network polling cadence remains 60 seconds. Increasing polling frequency can improve crossing-time resolution, but it cannot create server-side precision that is not present.

If a future Codex version begins returning meaningful decimal `usedPercent` values, the parser/data model must accept them without migration. Enabling a higher-precision estimator can then be a separate behavioral change.

## 5. Burn-rate model

### 5.1 Successful observations and crossing events are different things

Every successful usage poll creates an accepted **observation** for each valid quota:

```text
Observation {
  used_percent: f64,
  observed_at: i64,
  resets_at: Option<i64>,
}
```

A repeated integer value is still useful evidence and **must update the last successful observation time**. It simply does not create a new crossing event.

Example:

```text
12:00  10%
12:01  10%
12:02  11%
```

The second 10% observation proves that the 10 -> 11 transition occurred after 12:01. Therefore the estimated 11% crossing is:

```text
12:01:30
```

If repeated values were discarded completely, the estimator would incorrectly place the crossing somewhere between 12:00 and 12:02 and idle decay would also lose its right-side evidence.

Failed/rejected polls do not update `last_observed_at`.

### 5.2 Crossing interpolation

For the current integer-valued server output, when an accepted observation advances from integer level `a` to integer level `b > a`, create one crossing event for each crossed whole-percentage threshold.

For a one-point change:

```text
12:01  10%
12:02  11%
-> 11% crossing ~= 12:01:30
```

For a multi-point jump:

```text
12:00  10%
12:01  13%
```

distribute the three threshold crossings uniformly through the **observed interval**:

```text
11% ~= 12:00:15
12% ~= 12:00:30
13% ~= 12:00:45
```

For the current quantized integer output, if the observed jump contains `n = b - a` whole-percentage crossings, place crossing `j` (`1..=n`) at:

```text
crossing_time(j) =
  previous_time
  + (current_time - previous_time) * j / (n + 1)
```

This keeps every inferred threshold strictly inside the interval and gives the one-point case its midpoint. It intentionally models unknown crossing locations inside a quantized observation interval rather than pretending the integer endpoints are exact continuous usage values.

v1.3.0 uses these whole-percentage crossings for rate estimation. Raw `f64` values are nevertheless preserved so a future high-precision estimator can use decimal samples without changing the parser or persisted schema.

### 5.3 5-hour estimator — exact rule

The 5-hour rate is a recent, right-censored estimate.

1. Use only crossings from the current continuous observation segment and current quota cycle.
2. Let `latest` be the newest crossing.
3. Prefer an `earliest` crossing up to 3 percentage points below `latest`.
4. Require a crossing-level span of at least 2 percentage points. In practice this means at least three ordered threshold crossings, e.g. 11%, 12%, 13%.
5. Let `end_time` be the timestamp of the latest successful accepted observation, including an unchanged observation.
6. Compute:

```text
rate_pp_per_hour =
  (latest.level - earliest.level)
  / (end_time - earliest.time)
  * 3600
```

The right-side `end_time` is intentional. If the account stops consuming quota while successful polls continue, the numerator remains fixed while the denominator grows, so the recent rate decays naturally.

5-hour crossing evidence older than 30 minutes relative to `end_time` is not used to start a new estimate. Once the remaining evidence no longer provides the minimum 2-point span, the rate becomes unavailable (`None`) rather than preserving a stale active rate forever.

This produces the sequence:

```text
active estimate -> decaying estimate -> unavailable when evidence is too old
```

It does not fabricate an exact zero.

Unit:

```text
percentage points / hour
```

### 5.4 Weekly estimator — exact rule

Weekly usage moves more slowly and uses a longer horizon, but the same evidence rules apply.

- persist weekly state across normal app restarts;
- use crossings from the current continuous observation segment and current weekly quota cycle;
- prefer a recent span of 1-3 percentage points;
- require at least a **1 percentage-point crossing span** (two ordered threshold crossings) before emitting a rate;
- use the latest successful accepted observation as the right-side `end_time`;
- allow a substantially longer evidence horizon than the 5-hour estimator;
- return unavailable when the usable crossing span is insufficient.

The weekly estimator must not be forced into the 5-hour 30-minute horizon.

Use a starting weekly evidence horizon of 24 hours. Centralize it as a named constant so it is explicit, testable, and tunable rather than hidden in arithmetic.

### 5.5 Idle behavior

Burn Rate describes recent observed consumption, not the last moment at which the account was busy.

Repeated successful unchanged observations extend the right side of the estimate and therefore reduce the displayed rate.

A failed fetch does **not** count as evidence that usage stayed unchanged and must not advance idle decay.

When prior crossings age out of the estimator's evidence horizon, the display changes to unavailable rather than claiming `0.0%/h` from stale history.

### 5.6 Long gaps and discontinuities

Do not interpolate crossings across a long period during which the application was not successfully observing the account.

Examples:

- PC sleep;
- overlay not running;
- network/Codex unavailable for an extended period;
- resume after a long offline gap.

Use explicit per-quota maximum interpolation-gap constants. Recommended starting policy:

```text
5H:     10 minutes
Weekly: 6 hours
```

If the gap between the last accepted observation and the next valid observation exceeds the quota's maximum interpolation gap:

- do not synthesize crossings through the gap;
- begin a new continuous observation segment at the new sample;
- prior crossings may remain persisted for diagnostics/pruning, but must not be combined across the discontinuity to calculate a rate.

These constants must be covered by deterministic tests and can be tuned later without changing the state model.

### 5.7 Output formatting

Do not round every positive value blindly to one decimal if that would turn a small nonzero estimate into a semantic zero.

Recommended display:

```text
>= 0.05%/h  -> one decimal place, e.g. 0.6%/h
0 < rate < 0.05%/h -> <0.1%/h
unavailable -> —
```

`0.0%/h` should only be used if a later estimator explicitly has enough current evidence to classify the rate as effectively zero. v1.3.0 does not need to manufacture that state.

Also cap pathological display width with a defined presentation rule (for example `>999%/h`) so layout tests have a bounded maximum string.

## 6. Backend data model changes

Separate the protocol snapshot, estimator state, and frontend DTO. Do not make the UI-facing struct double as the raw app-server representation.

### 6.1 Raw protocol model

The parser should retain the server value as `f64`:

```rust
struct QuotaSnapshot {
    used_percent: Option<f64>,
    resets_at: Option<i64>,
    window_duration_mins: Option<u32>,
}

struct RawCodexUsage {
    account_id: Option<String>,
    five_hour: QuotaSnapshot,
    weekly: QuotaSnapshot,
    credits_display: String,
    credits_balance: Option<String>,
    has_credits: bool,
    fetched_at: i64,
}
```

Validation must reject non-finite/out-of-range values rather than coercing them into rate history.

The account identity is backend-only. It is used to prevent persisted rate history from one signed-in account being joined to another account after an account switch. It does not need to be exposed to React.

### 6.2 Estimator model

`BurnRateTracker` consumes `RawCodexUsage` / quota observations and owns:

- accepted observations;
- continuous-segment identity;
- crossing events;
- reset/correction handling;
- per-quota derived rates.

### 6.3 UI-facing model

The frontend receives only ready-to-render account state:

```rust
pub struct CodexUsage {
    pub five_hour_remaining_percent: Option<u32>,
    pub five_hour_burn_rate_per_hour: Option<f64>,

    pub week_remaining_percent: Option<u32>,
    pub week_burn_rate_per_hour: Option<f64>,

    pub credits_display: String,
    pub credits_balance: Option<String>,
    pub has_credits: bool,
    pub five_hour_resets_at: Option<i64>,
    pub week_resets_at: Option<i64>,
    pub fetched_at: i64,
}
```

The existing remaining-percentage display can continue to be integer-oriented. Raw `usedPercent` precision must not be lost before the estimator sees it.

The React layer must not implement quota math, crossing interpolation, reset logic, or idle decay.

## 8. Persistence

Reuse the existing `ConfigManager` and its temp-file + rename pattern.

Add:

```text
%LOCALAPPDATA%\CodexUsageOverlay\burn-rate-state.json
```

Keep burn-rate state separate from `reset-state.json`. Reset notifications and burn-rate estimation have different responsibilities and should not share one persistence schema.

Suggested persisted state:

```rust
BurnRateStateFile {
    schema_version: u32,
    account_id: Option<String>,
    five_hour: QuotaRateState,
    weekly: QuotaRateState,
}

QuotaRateState {
    resets_at: Option<i64>,
    segment_id: u64,
    last_observed_percent: Option<f64>,
    last_observed_at: Option<i64>,
    correction_candidate: Option<CorrectionCandidate>,
    crossings: Vec<CrossingEvent>,
}
```

Persistence must preserve repeated successful unchanged observations because `last_observed_at` is part of the estimator's right-side evidence.

For v1.3.0, the simplest reliable policy is:

- after every accepted successful network observation that changes persisted tracker state, atomically save `burn-rate-state.json`;
- failed or rejected samples do not write estimator state;
- the one-second React countdown tick never writes this file.

At a 30-300 second network cadence the file is tiny, so one atomic write per accepted poll is preferable to relying on graceful application exit and losing right-censoring evidence after a crash/reboot.

If the returned account identity differs from the persisted account identity:

- clear both quota histories/correction candidates;
- establish fresh baselines for the new account;
- persist the new account identity before producing a cross-account rate.

Bound crossing history to a small fixed count. A few dozen events per quota is more than enough.

## 9. Reset, correction, and stale-sample handling

The project already has reset-boundary semantics in `notify.rs`. Burn-rate state must remain a separate module, but its definition of an actual cycle transition must be compatible with that existing behavior.

### 9.1 A future `resetsAt` shift is not automatically a reset

The existing notification logic intentionally distinguishes:

```text
server moves a future boundary
!=
the old quota cycle has actually completed
```

Therefore Burn Rate must **not** clear history merely because a larger `resetsAt` value appears while the previously accepted boundary is still in the future.

For each quota, retain enough cycle metadata to distinguish:

- initial boundary observation;
- future boundary correction/update;
- actual transition after the old boundary has been crossed.

Only an actual accepted cycle transition clears that quota's crossing/observation segment and establishes a new baseline.

5H and weekly resets remain fully independent.

### 9.2 Percent regression inside the same cycle

A lower `usedPercent` with no accepted cycle transition is suspicious but cannot be rejected forever, because the server may legitimately correct its accounting.

Use a correction-candidate rule:

1. first regressed sample in the same cycle:
   - do not create crossings;
   - do not emit a negative rate;
   - store it as `correction_candidate`;
2. if the next successful observation returns to the old monotonic range:
   - discard the candidate as stale/out-of-order;
3. if a second consecutive successful observation confirms the lower range:
   - accept a server correction;
   - clear that quota's current crossing history;
   - increment/start a new continuous segment;
   - establish the confirmed lower observation as the new baseline;
   - persist the correction.

This prevents one stale response from corrupting the estimator while avoiding a tracker that can become permanently stuck after a real server correction.

### 9.3 Account switch

If a valid returned account identity changes:

- clear both 5H and weekly tracker histories;
- clear both correction candidates;
- establish fresh baselines;
- do not combine pre-switch and post-switch samples.

### 9.4 Invariants

- never emit a negative burn rate;
- stale/rejected samples never create crossings;
- failed reads never advance idle inference;
- future reset-boundary adjustments do not erase valid history;
- 5H reset must not erase weekly history;
- weekly reset must not erase current 5H history;
- the existing notification reset-state remains the authority for notification behavior and must not be behaviorally changed by Burn Rate.

## 10. Usage pipeline cleanup

There are currently two nearly adjacent startup network-fetch paths:

1. Rust background loop waits approximately 500 ms and runs `fetch_usage_background()`.
2. React `App.tsx` calls `handleRefresh()` during main-window startup.

Both serialize through the same `CodexClient` mutex, but the second network request is unnecessary.

v1.3.0 should make the Rust backend the single owner of automatic network polling.

However, simply deleting the React startup fetch introduces an event-order race: the first backend `usage_updated` event can occur before the React listener has finished registering, and Tauri events are not a replayable state store.

Use this startup contract instead:

```text
app startup
  -> backend polling task owns network fetches
  -> backend stores every successful rendered CodexUsage in last_usage
  -> React awaits successful registration of the usage_updated listener
  -> React invokes get_last_usage() (cache-only; MUST NOT fetch network)
  -> if cached usage exists, render it
  -> future usage_updated events replace it
```

The initial backend fetch may occur before or after the frontend becomes ready; **listener registration must complete before the cache read**. That ordering guarantees that a fetch occurring between the two operations is either observed as an event or already present in `last_usage`, so no first sample can fall into a gap.

`get_last_usage()` must be a cheap read-only command over backend state. It must not spawn `codex app-server`.

Manual refresh remains available and should call the same backend network service path used by the automatic poller.

## 11. Unify duplicated fetch processing

The current command path and background path both contain similar:

```text
lock client
write status = reading
fetch_usage()
on success:
  write status = ok
  process_usage_success()
on failure:
  write status = error
  update tray state
```

Refactor to one internal backend service operation that owns the full network-sample transaction:

```text
refresh_usage()
  -> mark reading
  -> acquire fetch/client guard
  -> fetch RawCodexUsage
  -> release client I/O lock immediately
  -> BurnRateTracker.accept(...)
  -> persist tracker if state changed
  -> build UI-facing CodexUsage
  -> update last_usage
  -> write status
  -> tray update
  -> reset notification processing
  -> usage_updated emission
```

The `CodexClient` mutex must be held only for app-server I/O. Do not keep it locked while performing persistence, tray work, notifications, docking work, or event emission.

The unified service should own:

- client access;
- raw usage fetch and validation;
- BurnRateTracker update;
- burn-rate persistence;
- UI DTO construction;
- `last_usage`;
- status file;
- tray update;
- reset notification processing;
- `usage_updated` emission.

Then:

- background polling calls it;
- manual refresh calls it;
- post-reset fetch calls it or a clearly documented variant.

Prefer a single in-flight refresh guard/coalescing seam so simultaneous background/manual/post-reset triggers do not queue multiple redundant app-server processes. Exact coalescing mechanics are implementation detail, but the behavior must be tested.

This avoids feature drift between manual and automatic reads and keeps estimator mutation exactly-once per accepted network sample.

## 12. Polling cadence

Keep the existing user-configurable refresh interval and default of 60 seconds.

Burn-rate quality depends on that interval:

- 30 s: better crossing-time resolution;
- 60 s: recommended balance;
- 120 s: usable but coarser;
- 300 s: noticeably coarse for fast 5H consumption.

Do not add 1-second network polling.

The existing one-second React tick remains for reset countdown display. Burn rate does not require another timer.

For v1.3.0, the displayed burn-rate value updates only when a successful real usage sample is processed. Repeated unchanged successful samples are meaningful because they advance the estimator's right-side observation time.

Do not locally advance burn-rate decay on the one-second UI timer: doing so would make the display imply observations that the server has not confirmed.

Long-gap handling from §5.6 is independent of the configured nominal refresh interval. A delayed/failed poll does not become evidence merely because a timer elapsed.

A later version may add a clearly labeled purely local prediction/interpolation layer if user testing shows that once-per-poll updates feel too static, but that must remain distinct from the observed Burn Rate.

## 14. Display preference decision

Do **not** add `showBurnRate` in v1.3.0.

Burn Rate is part of the expanded overlay's core information design for this release:

- expanded 5H and WK blocks show it on the second row;
- Credits never shows it;
- collapsed edge pill never shows it.

This avoids adding a Rust/TypeScript settings field, patch validation, SettingsView control, three-language i18n copy, migrations, and tests before there is evidence that users need a switch.

If real-world width/usability feedback later justifies a display preference, it can be added independently. BurnRateTracker should continue to collect history regardless of future display preference.

## 15. Follow-up architecture experiment — persistent app-server

The current Rust client starts and kills a new `codex app-server` for every usage request.

A persistent connection might reduce process spawn frequency, repeated initialize calls, and per-fetch latency. It could also add resident memory, reconnect logic, and long-lived-process failure modes.

This experiment is explicitly **not part of v1.3.0 Burn Rate release scope**.

After v1.3.0 is complete, a separate benchmark/decision document may compare:

Transient mode:

- average fetch latency;
- process startup latency;
- CPU during a fetch;
- hourly process spawn count.

Persistent mode:

- resident memory of idle app-server;
- idle CPU;
- fetch latency;
- reconnection behavior;
- multi-hour stability.

Adopt a persistent app-server only if measurements justify the resident cost and complexity. Burn Rate must work correctly with the existing transient client.

## 16. Error and compatibility behavior

If usage fetch fails:

- keep last good quota/rate data in memory;
- preserve current error status / tray behavior;
- do not create new crossing events;
- do not update `last_observed_at`;
- do not advance idle inference from a failed server sample as though it were a confirmed unchanged quota reading.

If a quota sample is structurally present but `usedPercent` is non-finite or outside 0-100:

- reject that quota observation from BurnRateTracker;
- do not coerce it into history;
- continue processing other independently valid fields where possible.

If Codex changes or removes the relevant account fields:

- remaining percentage may become unavailable;
- burn rate becomes unavailable;
- Credits and other valid fields should continue rendering where possible.

Missing account identity must not by itself break usage display. It only disables positive account-switch detection for that observation.

The feature must remain tolerant of missing `primary`, `secondary`, reset timestamps, `windowDurationMins`, or account identity.

## 19. Acceptance criteria

v1.3.0 Burn Rate work is complete when:

- current 5H / WK / Credits values remain behaviorally correct;
- reset countdowns remain correct;
- reset notifications remain behaviorally unchanged;
- the parser preserves raw `usedPercent` as `f64` even though the current server output is integer-valued;
- 5H and weekly Burn Rate are derived from account-level observed crossings without inventing hidden decimal precision;
- repeated successful unchanged samples advance right-side evidence without creating crossings;
- failed samples do not advance idle inference;
- long unobserved gaps never receive uniformly fabricated crossing history;
- future `resetsAt` changes are not mistaken for completed resets;
- confirmed same-cycle server corrections rebaseline safely;
- account switches cannot combine histories;
- rate text is displayed on the **second row, to the right of the reset countdown**;
- unavailable, tiny-positive, normal, and pathological-high rates use the defined bounded display semantics;
- no rate is added to Credits;
- collapsed edge pill remains unchanged;
- no third UI row is introduced;
- no Burn Rate preference is added in v1.3.0;
- no 1-second network polling is introduced;
- valid same-segment weekly history survives normal restart;
- resets do not contaminate the other quota's history;
- stale samples cannot create negative rates;
- manual, automatic, and post-reset refresh use one backend processing path;
- duplicate/redundant concurrent refreshes do not mutate the estimator more than once per real sample;
- the duplicate React startup network fetch is removed;
- cache-only `get_last_usage()` prevents first-event loss at startup;
- final width remains content-driven while provisional dock geometry is updated for the wider capsule;
- all frontend/Rust/build/check gates pass;
- real-machine layout checks pass at supported scale/DPI/layout combinations.

## 21. Product interpretation

The new field answers:

> At the recent observed account-consumption rate, how many percentage points of this quota window are being consumed per hour?

It does **not** claim to be model decoding speed, exact instantaneous billing speed, or a guarantee of future quota consumption.

The first-row percentage remains the primary state. Burn Rate is deliberately placed in the spare area beside the reset countdown so it remains useful without changing the overlay's existing visual hierarchy.
