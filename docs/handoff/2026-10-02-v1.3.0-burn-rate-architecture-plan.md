# Codex Usage Overlay v1.3.0 — Burn Rate + Architecture Optimization Plan

**Date:** 2026-10-02  
**Project:** `D:\OneDrive\AiPrograms\codex tools\codex-usage-overlay`  
**Baseline:** v1.2.1 / `main` / `751a4f9`

## 1. Goal

Add account-level quota burn-rate estimates to the existing 5-hour and weekly quota display while preserving the current compact overlay layout and all existing v1.2.1 behavior.

Primary new metrics:

- 5-hour burn rate: percentage points of the 5-hour quota consumed per hour.
- Weekly burn rate: percentage points of the weekly quota consumed per hour.

The feature deliberately replaces the need for token/s as the primary practical speed metric. It measures how quickly the account allowance is actually being consumed across all simultaneous Codex sessions.

## 2. Current architecture audit

The existing project already has the right overall technology stack and should **not** be rewritten.

Current stack:

- Tauri 2
- Rust backend
- React / TypeScript frontend
- WPF/C# migration is **not** recommended for this repository.

Current usage path:

```text
background polling
  -> CodexClient::fetch_usage()
  -> spawn codex app-server --stdio
  -> initialize
  -> account/rateLimits/read
  -> parse CodexUsage
  -> process_usage_success()
  -> usage_updated event
  -> React OverlayView
```

The account-level `account/rateLimits/read` source should be retained. It already aggregates all concurrent Codex sessions and avoids reading `auth.json`, scraping the UI, or merging session logs.

## 3. Confirmed constraints

The currently exposed account usage values are integer percentage steps. Local inspection of `account/rateLimits/read` and local Codex rate-limit records did not reveal higher-precision decimal values suitable for production use.

Therefore v1.3.0 must:

- use integer quota crossings as the source of truth;
- derive rate from crossing time rather than invent decimal usage precision;
- keep the existing account API;
- avoid HTTP/WebSocket proxying, token-stream interception, session-log aggregation, or custom Codex builds.

The default network polling cadence remains 60 seconds. Increasing polling frequency does not recover missing quota precision and should not be used as a substitute for a better estimator.

## 4. UI requirement — exact placement

The new rate field must **not** be placed beside the large percentage on the first row.

In the normal expanded overlay, each quota block currently has:

```text
5H  90%
2h 34m
```

and:

```text
WK  98%
6d 21h
```

The v1.3.0 target is:

```text
5H  90%
2h 34m   16.8%/h
```

```text
WK  98%
6d 21h   0.6%/h
```

The burn-rate field occupies the unused horizontal space **to the right of the reset countdown on the second row**.

This is a hard layout requirement.

### 4.1 Visual hierarchy

First row remains dominant:

- quota label;
- large remaining percentage.

Second row remains secondary:

- reset countdown on the left;
- burn rate on the right.

The burn-rate text should use the same visual weight class as the reset countdown or only slightly stronger. It must not visually compete with the large remaining percentage.

Recommended first implementation:

```text
2h 34m    16.8%/h
```

rather than adding an extra label such as `RATE`, `BR`, or `Burn`.

### 4.2 Credits block

Credits remain unchanged. No rate field is added under `CR`.

### 4.3 Docked/collapsed pill

The collapsed edge pill remains unchanged in v1.3.0. It continues to show only quota bars and optional percentage grid.

Burn rate is shown only when the overlay is expanded.

### 4.4 Layout modes

Both `grouped` and `stacks` modes should support the rate.

For each 5H/WK quota block, the second row becomes a two-item horizontal row:

```text
[countdown]    [burn rate]
```

If the available width is insufficient, preserve the countdown first and allow the overall capsule width to grow. Do not wrap the burn rate onto a third line.

## 5. Burn-rate model

### 5.1 Record quota crossings, not every poll

A poll that repeats the same integer value does not create a new crossing.

Example:

```text
12:00  10%
12:01  10%
12:02  11%
```

The 10 -> 11 transition happened somewhere between 12:01 and 12:02. Estimate its crossing time at the midpoint:

```text
12:01:30
```

This reduces 60-second polling quantization error without pretending to know a more precise server value.

### 5.2 Multi-point jump

If one poll jumps several percentage points:

```text
12:00  10%
12:01  13%
```

distribute the crossings uniformly through the interval:

```text
11% ~= 12:00:15
12% ~= 12:00:30
13% ~= 12:00:45
```

### 5.3 5-hour estimator

Use a short quota-distance window rather than a fixed time window.

Recommended policy:

- target the most recent 3 percentage points;
- minimum useful history: 2 percentage points;
- maximum lookback: approximately 30 minutes;
- include current time as a right-side constraint so an idle account naturally reduces the displayed recent rate;
- if evidence is insufficient, return unavailable rather than a fabricated value.

Unit:

```text
percentage points / hour
```

Display with one decimal place.

### 5.4 Weekly estimator

Weekly usage moves more slowly, so it needs its own estimator.

Recommended policy:

- persist across app restarts;
- use the most recent 1-3 percentage points;
- allow a multi-hour lookback within the current weekly quota cycle;
- require at least one observed weekly crossing before showing an estimate;
- return unavailable when evidence is insufficient.

Do not force the weekly estimator into the 5-hour time horizon.

### 5.5 Idle behavior

The rate is intended to describe recent burn, not permanently preserve the last active rate.

If quota usage stops changing, the displayed 5-hour rate must decay over time toward zero as the previous crossings become less representative.

Weekly rate may decay more slowly because it is intentionally a longer-horizon estimate.

## 6. Backend data model changes

Extend Rust `CodexUsage` with raw used-percent and derived rate fields.

Proposed shape:

```rust
pub struct CodexUsage {
    pub five_hour_used_percent: Option<u32>,
    pub five_hour_remaining_percent: Option<u32>,
    pub five_hour_burn_rate_per_hour: Option<f64>,

    pub week_used_percent: Option<u32>,
    pub week_remaining_percent: Option<u32>,
    pub week_burn_rate_per_hour: Option<f64>,

    pub credits_display: String,
    pub credits_balance: Option<String>,
    pub has_credits: bool,
    pub five_hour_resets_at: Option<i64>,
    pub week_resets_at: Option<i64>,
    pub fetched_at: i64,
}
```

The frontend should receive a ready-to-render burn rate. The React layer must not implement quota math.

## 7. New Rust module

Add a dedicated module, for example:

```text
src-tauri/src/codex/
  client.rs
  finder.rs
  burn_rate.rs
  mod.rs
```

`burn_rate.rs` owns:

- quota sample normalization;
- crossing detection;
- midpoint / multi-crossing interpolation;
- stale-value rejection;
- reset detection;
- 5H estimator;
- weekly estimator;
- idle decay;
- bounded history.

This logic should be testable without Tauri, Codex, network access, or a real clock.

Use explicit timestamps in tests instead of calling wall-clock time from inside the estimator.

## 8. Persistence

Reuse the existing `ConfigManager` and its temp-file + rename pattern.

Add:

```text
%LOCALAPPDATA%\CodexUsageOverlay\burn-rate-state.json
```

Keep burn-rate state separate from `reset-state.json`. Reset notifications and burn-rate estimation have different responsibilities and should not share one persistence schema.

Suggested persisted state:

```rust
BurnRateStateFile {
    schema_version: u32,
    five_hour: QuotaRateState,
    weekly: QuotaRateState,
}

QuotaRateState {
    resets_at: Option<i64>,
    last_sample_percent: Option<u32>,
    last_sample_at: Option<i64>,
    crossings: Vec<CrossingEvent>,
}
```

Persist only when needed:

- first valid baseline;
- percentage changes;
- reset boundary changes;
- accepted state correction;
- graceful application exit if in-memory state differs.

Do not write the file on every one-second UI tick.

Bound crossing history to a small fixed count. A few dozen events per window is more than enough.

## 9. Reset and stale-sample handling

The project already has robust reset-boundary logic for notifications. Burn-rate state should use compatible rules but remain a separate module.

For each quota independently:

- if `resetsAt` advances to a new accepted quota cycle, clear that quota's rate history and establish a new baseline;
- if `usedPercent` decreases while `resetsAt` has not advanced, treat the sample as stale/inconsistent and reject it;
- never emit a negative burn rate;
- 5H reset must not erase weekly history;
- weekly reset must not erase current 5H history.

The existing notification reset-state remains the source for notification behavior. Burn-rate code must not change reset-notification semantics.

## 10. Usage pipeline cleanup

There are currently two nearly adjacent initial-fetch paths:

1. Rust background loop waits approximately 500 ms and runs `fetch_usage_background()`.
2. React `App.tsx` calls `handleRefresh()` during main-window startup.

Both eventually serialize through the same `CodexClient` mutex, but the second initial request is unnecessary.

v1.3.0 should make the Rust backend the single owner of automatic polling.

Recommended behavior:

```text
app startup
  -> backend polling task
  -> first fetch after short startup delay
  -> process success/error
  -> emit usage_updated
  -> React renders event
```

React should not issue its own startup fetch.

Manual refresh remains available and should call the same backend service path used by the automatic poller.

## 11. Unify duplicated fetch processing

The current command path and background path both contain similar:

```text
lock client
write status = reading
fetch_usage()
on success:
  write status = ok
  process_usage_success()
on failure:
  write status = error
  update tray state
```

Refactor to one internal backend function / service operation that owns:

- client access;
- usage fetch;
- BurnRateTracker update;
- persistence;
- `last_usage`;
- status file;
- tray update;
- reset notification processing;
- `usage_updated` emission.

Then:

- background polling calls it;
- manual refresh calls it;
- post-reset fetch calls it or a clearly documented variant.

This avoids future feature drift between manual and automatic reads.

## 12. Polling cadence

Keep the existing user-configurable refresh interval and default of 60 seconds.

Burn-rate quality depends on that interval:

- 30 s: better crossing-time resolution;
- 60 s: recommended balance;
- 120 s: usable but coarser;
- 300 s: noticeably coarse for fast 5H consumption.

Do not add 1-second network polling.

The existing one-second React tick remains for reset countdown display. Burn rate does not require another timer.

For v1.3.0, the displayed burn-rate value may update when a new real usage sample arrives. Do not add a second backend event loop solely to animate the number between network samples.

A later version may add purely local interpolation if user testing shows that once-per-poll updates feel too static.

## 13. Frontend integration

Update `src/types.ts` so `CodexUsage` includes the two new burn-rate fields.

In `OverlayView.tsx`, keep the existing quota block structure but replace the single countdown span with a second-row container.

Conceptually:

```tsx
<div className="overlay-meta-row">
  <span className="overlay-countdown">{quota.countdown}</span>
  <span className="overlay-burn-rate">{quota.burnRateText}</span>
</div>
```

Recommended rendering:

```text
quota rate unavailable -> —
quota rate available   -> 16.8%/h
```

Do not show `0.0%/h` merely because there is not enough evidence. Reserve `0.0%/h` for a state where the estimator has enough history to conclude the recent rate is effectively zero.

### 13.1 Width and sizing

The new second-row field will widen each quota block.

The existing sizing architecture is favorable:

- `ResizeObserver` measures real rendered content;
- the main window resizes dynamically;
- docked expanded windows are repositioned after resize.

Still, v1.3.0 must explicitly verify:

- no clipping in Chinese, Traditional Chinese, or English;
- both `grouped` and `stacks` layouts;
- scale range 100%-250%;
- Windows text scaling / DPI compensation;
- auto-edge-hide expanded state;
- Credits shown and hidden;
- 5H / WK rates with short and long strings.

No hardcoded width should be introduced just for Burn Rate.

### 13.2 Styling

Recommended style intent:

- countdown remains muted secondary text;
- burn rate uses the same font size;
- burn rate may use slightly higher opacity than countdown;
- rate color remains neutral and does not inherit green/yellow/red quota health colors.

Example:

```text
5H  90%
2h 34m    16.8%/h
```

The two values should read as one metadata row, not two unrelated labels.

## 14. Optional display preference

Because this is a public utility and the new field increases width, add a user preference:

```text
showBurnRate: boolean
```

Recommended default: `true`.

When disabled:

- the second row returns to the current countdown-only layout;
- BurnRateTracker may continue collecting history in the backend so re-enabling does not require relearning the quota rate;
- no change to Credits or collapsed pill.

This setting must be added to:

- Rust `OverlaySettings`;
- default settings;
- patch allowlist;
- TypeScript `OverlaySettings`;
- frontend default settings;
- SettingsView;
- i18n strings in all supported languages;
- round-trip / allowlist tests.

If width testing shows that always-on Burn Rate is acceptable and product direction prefers no extra setting, this subsection may be dropped before implementation. The estimator architecture is unaffected.

## 15. App-server process optimization

The current Rust client still starts and kills a new `codex app-server` for every usage request.

A persistent connection could reduce:

- process spawn frequency;
- repeated initialize calls;
- per-fetch latency.

However, unlike the old PowerShell prototype, this Tauri app already avoids spawning an extra PowerShell process on each fetch. A persistent app-server may cost more idle RAM than it saves.

Therefore this optimization is **benchmark-gated**, not automatically part of the Burn Rate implementation.

### 15.1 Benchmark

Measure current transient mode:

- average fetch latency;
- process startup latency;
- CPU during a fetch;
- hourly process spawn count.

Prototype persistent mode and measure:

- resident memory of idle app-server;
- idle CPU;
- fetch latency;
- reconnection behavior;
- multi-hour stability.

Decision rule:

- adopt persistent app-server only if measured latency/process savings justify its resident cost and complexity;
- otherwise keep transient `fetch_usage()`.

Burn Rate must not depend on this decision.

## 16. Error and compatibility behavior

If usage fetch fails:

- keep last good quota/rate data in memory;
- preserve current error status / tray behavior;
- do not create new crossing events;
- do not advance idle inference from a failed server sample as though it were a confirmed unchanged quota reading.

If Codex changes or removes the relevant account fields:

- remaining percentage may become unavailable;
- burn rate becomes unavailable;
- Credits and other valid fields should continue rendering where possible.

The feature must remain tolerant of missing `primary`, `secondary`, or reset timestamps.

## 19. Acceptance criteria

v1.3.0 Burn Rate work is complete when:

- current 5H / WK / Credits values remain correct;
- reset countdowns remain correct;
- reset notifications remain behaviorally unchanged;
- 5H and weekly burn-rate fields are derived from account-level integer quota crossings;
- rate text is displayed on the **second row, to the right of the reset countdown**;
- no rate is added to Credits;
- collapsed edge pill remains unchanged;
- no third UI row is introduced;
- no 1-second network polling is introduced;
- weekly rate history survives overlay restart within the same quota cycle;
- resets do not contaminate the other quota's history;
- stale samples cannot create negative rates;
- manual and automatic refresh use one backend processing path;
- the duplicate startup fetch is removed;
- all frontend/Rust/build/check gates pass;
- real-machine layout checks pass at supported scale/DPI/layout combinations.

## 20. Out of scope for v1.3.0

Do not add:

- token/s;
- inference TPS;
- session-level rate breakdown;
- model-level allowance attribution;
- raw HTTP/SSE interception for decimal quota values;
- WebSocket proxying;
- SQLite;
- long-term analytics dashboard;
- per-second account polling.

## 21. Product interpretation

The new field answers:

> At the recent observed account-consumption rate, how many percentage points of this quota window are being consumed per hour?

It does **not** claim to be model decoding speed, exact instantaneous billing speed, or a guarantee of future quota consumption.

The first-row percentage remains the primary state. Burn Rate is deliberately placed in the spare area beside the reset countdown so it remains useful without changing the overlay's existing visual hierarchy.
