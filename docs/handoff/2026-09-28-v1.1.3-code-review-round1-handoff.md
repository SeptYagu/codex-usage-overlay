## 二、审查发现与缺陷清单

### P2-1 混合 DPI 多显示器下，设置窗口几何恢复会选中错误的显示器（相交校验假阳性 + 首个命中即采用）

**文件与行号**
- 保存：`src-tauri/src/lib.rs:55-70`（`x/y/width/height` = 物理值 ÷ `window.scale_factor()`，落盘为“逻辑”值）
- 判定：`src-tauri/src/tray.rs:287-304` `geometry_intersects_work_area`（用**候选显示器自己的** `scale_factor()` 把逻辑矩形换算到物理空间）
- 选取：`src-tauri/src/tray.rs:240-249`（`find(...)` — 第一个命中的显示器即被采用，不比较重叠面积，也没有“保存时所在显示器”这一锚点）
- 应用：`src-tauri/src/tray.rs:251-274`

**触发条件**
≥2 台显示器且缩放比不同（例如主屏 1920×1080 @100%、副屏 2560×1440 @150%；或笔记本 150% + 外接屏 100%）；设置窗口被放在缩放比较高的那块屏上；关闭设置窗口（触发保存）→ 退出应用 → 重启 → 从托盘打开设置。

**实际行为 vs 期望行为**
- 实际：`available_monitors()` 中主屏（scale 1.0）先命中，窗口被恢复到主屏上的 `x = 保存逻辑值 × 1.0`（示例中物理 1333,133），跳到了另一块屏幕。
- 期望：恢复到副屏原位置（示例中物理 2000,200，逻辑 480×660 不变）。

**根因**
1. `SettingsWindowGeometry` 存的是**与保存时显示器 scale 绑定的逻辑值**，但恢复时对每一个候选显示器都用**该显示器自己的 scale** 去反算这个逻辑矩形。同一个逻辑矩形被投影到不同 DPI 的坐标系里会得到不同的物理矩形 —— 示例中投影到 scale 1.0 的主屏得到 `[1333.3, 1813.3]`，完全落在主屏工作区 `[0,1920]` 内，而真实窗口在副屏上 → **假阳性**；同理，真机在副屏上也可能被判为不相交而落到居中兜底。
2. 选取用 `find()` 取第一个命中者，重叠面积不参与比较。由于假阳性同时存在于“真屏”和“投影屏”上，结果完全由枚举顺序决定；Windows 通常先枚举主屏，因此实际表现是稳定地选错。

**复现方法 / 运行证据**
1. 独立复算（照搬 `tray.rs:230-304` 算式，布局 M1=1920×1080@1.0(0,0)、M2=2560×1440@1.5(1920,0)；窗口真实在 M2，物理 (2000,200)、内尺寸 720×990 → 保存值 `{x:1333.33,y:133.33,w:480,h:660}`）：
   - 主屏优先枚举 → `PRIMARY-100% size=(480x660) pos=(1333,133)` ← **错误**
   - 副屏优先枚举 → `SECONDARY-150% size=(720x990) pos=(2000,200)` ← 正确
   - `intersects(PRIMARY, saved) = true`（假阳性）、`intersects(SECONDARY, saved) = true` → 命中集合与顺序共同决定结果
   - 对照组：同缩放比（1.0/1.0）双屏 → `SEC-100% size=(720x660) pos=(2000,200)` 正确 ⟹ 缺陷仅在混合 DPI 下出现
2. 实机复现步骤（本机无法执行，见 §三）：两块缩放比不同的屏 → 把设置窗口拖到副屏并调整尺寸 → 点设置窗口的关闭按钮 → 托盘退出并重启 → 从托盘打开设置，观察窗口落在哪块屏。

**影响范围**
本版本核心交付之一（位置记忆）在“笔记本 + 外接屏不同缩放”这一常见配置下失效：窗口会跳到另一块屏幕（仍在工作区内，不会造成幽灵窗口，逻辑尺寸也保持一致）；单屏、同 DPI 多屏、DPI 变化后的单屏场景均正确。不会引发崩溃或数据问题。

**修复建议**
- 保存时把“窗口当时所在显示器的 `scale_factor`”（或直接存物理矩形 + 显示器 `name`）一并落盘；结构体新增字段须带 `#[serde(default)]` 以兼容已存在的旧文件。
- 恢复时用**保存时的 scale** 把矩形换算回物理空间再与各显示器工作区求交；或对每个显示器计算重叠面积、取面积最大且 > 0 者，从根本上消除“投影假阳性 + 顺序敏感”。
- 把“选择显示器”抽成不依赖 `AppHandle` 的纯函数，便于补单测。

**修复后验收标准**
1. 100%/150% 混合布局、窗口位于副屏：重启后恢复到副屏且物理位置与逻辑尺寸均一致。
2. 显示器枚举顺序正序、逆序两种都能得到同一个（正确的）显示器。
3. 原显示器被拔出时退化为居中兜底，而不是恢复到未连接显示器的坐标。
4. 新增覆盖上述三条的纯几何单测（含假阳性布局与顺序两种输入）。

### P3-1 托盘菜单宽度未做自适应，验收标准中的“自适应宽度”未落地（计划文档的对应说明与代码不符）

**文件与行号**
- `src-tauri/src/tray.rs:101` `layout_tray_menu(app, generation, revision, height_logical)` —— 只接收高度
- `src-tauri/src/tray.rs:148` `let width = (300.0 * scale).ceil() as i32;` —— 宽度恒为 300 逻辑像素
- `src/components/TrayMenuView.tsx:47-66` `measureMenu()` —— 只测量 `getBoundingClientRect().height`
- `docs/handoff/2026-09-28-v1.1.3-update-plan.md` §3：“依托原有 `measureMenu()` 自动重算托盘弹出窗口尺寸，保证扩展文本不折行、不遮挡”

**触发条件**
任一语言的“检查更新”文案宽度超过可用内容宽度：300 − 2×10（外层 `p-2.5`）− 2×10（`.tray-menu-item` padding，见 `src/index.css:141-153`）= **260 逻辑像素**。例如未来更长的翻译，或用户在 Windows 上放大“文本大小”。

**实际行为 vs 期望行为**
- 实际：托盘弹出窗口宽度恒为 300 逻辑像素，宽度从不参与重算；`{{version}}` 插值后的长文案只能依赖 `.tray-menu-item` 的自动折行（该规则没有 `white-space: nowrap`），随后由高度重算把窗口撑高。
- 期望（按验收标准 3 与计划 §3 的措辞）：宽度随最宽菜单项自适应，且不折行。

**根因**
计划里“重算尺寸”的能力只覆盖高度轴：`measureMenu` 只上报 `heightLogical`，后端只接受 `heightLogical`，宽度是编译期常量。前端也没有上报测量宽度。

**影响范围**
当前**无可见缺陷**：三语插值后文案宽度解析估算约 165–205 px（CJK 全角按 13 px/字、西文约 7 px/字），距 260 px 仍有 55–95 px 余量，可单行容纳。属验收口径/健壮性问题：文案一旦变长即与“不折行”的承诺不符，且“自适应宽度”这一验收条目在当前实现里不存在对应代码路径（属“表面完成”）。

**复现方法 / 运行证据**
阅读 `layout_tray_menu` 签名与 `tray.rs:148` 常量即可确认宽度不参与测量；`tray.rs:148` + `tray.rs:101` + `TrayMenuView.tsx:51` 三处构成完整证据链。（像素级实测受环境限制未做，见 §三。）

**修复建议**
- 前端 `measureMenu` 一并上报内容宽度（`scrollWidth`/`getBoundingClientRect().width`），`layout_tray_menu` 增加 `width_logical` 参数并按工作区 `clamp`。
- 或维持固定宽度，但把验收口径与计划文档统一改为“不截断（必要时折行）”，并补一条断言菜单项单行渲染（`scrollWidth <= clientWidth`）的测试。

**修复后验收标准**
三语文案下托盘菜单项均单行呈现且无横向截断；或口径明确改为允许折行，且计划文档同步更正、测试断言与之一致。

### P3-2 几何仅在设置窗口关闭时落盘，从托盘退出 / 关机路径不会持久化

**文件与行号**
- `src-tauri/src/lib.rs:55-70` —— 全仓唯一的保存点（`save_settings_geometry` 仅在此处被调用）
- `src-tauri/src/lib.rs:253-258` `RunEvent::Exit` —— 只处理音频与已准备更新，未兜底保存几何
- `src-tauri/src/tray.rs:191-224` —— 打开时才恢复

**触发条件**
打开设置 → 调整大小/移动 → 不点设置窗口的关闭按钮，直接从托盘“退出悬浮窗”（`exit_app`）或系统关机 / 任务管理器结束进程 → 重启 → 从托盘打开设置。

**实际行为 vs 期望行为**
- 实际：使用上一次“成功关闭设置窗口”时保存的几何（若从未保存过则居中 480×660）；本次调整丢失。
- 期望（验收标准 2“允许自由调整大小并跨会话安全持久化”）：本次调整被持久化。

**根因**
只有 `WindowEvent::CloseRequested` 一条落盘路径，退出路径没有兜底，也没有对 `Resized`/`Moved` 做防抖保存。

**影响范围**
“调整后直接退出”这一路径下跨会话记忆失效；有明确规避方案（先关闭设置窗口再退出），不阻塞。

**复现方法 / 运行证据**
静态可确认：`grep -rn "save_settings_geometry" src-tauri/src` 只有 `config.rs` 定义与 `lib.rs:66` 一处调用。实机步骤见 §三。

**修复建议**
在 `RunEvent::Exit`（或 `ExitRequested`）里读一次设置窗口几何并保存；或对 `WindowEvent::Resized`/`Moved` 做 500 ms 防抖落盘。

**修复后验收标准**
调整尺寸后直接从托盘退出并重启，尺寸与位置复原；退出后运行目录无残留 `*.json.tmp`。

## 三、待确认风险与未验证项

1. **未验证（环境限制，涉及 P2-1 / P3-1 / P3-2 的实机面）**：所有需要真实窗口、真实多显示器/DPI、真实托盘交互的场景无法在本机只读审查中执行。需要一台带 ≥2 块缩放比不同的显示器、可运行打包后 GUI 的 Windows 机器。由此产生的残余风险：
   - P2-1 的实机表现依赖“混合 DPI 布局下 Windows 先枚举主屏”这一假设；本文的假阳性结论与顺序无关（两种顺序都至少有一块错误候选同时命中），但“最终稳定选错主屏”的具体落点需实机确认。
   - P3-1 的文案宽度为解析估算而非像素级实测；估算余量（55–95 px）较大，不足以改变结论，但“是否折行”的最终判定建议实机截图确认。
2. **残留风险（非阻塞建议）**：`src/version.ts:1` 的 `APP_VERSION = '1.1.3'` 是硬编码常量，与 5 处配置的一致性目前完全依赖人工同步，仓库没有任何门禁校验这 6 处一致；新增测试 `src/components/TrayMenuView.test.tsx:60` 断言的是字面量 `'v1.1.3'`，只能证明 `version.ts` 自身的值，无法发现 `version.ts` 与 `tauri.conf.json`/`package.json` 的漂移。建议加入一处读取 `package.json` 与 `tauri.conf.json` 的一致性断言，或改用 `@tauri-apps/api/app` 的 `getVersion()`（由构建产物提供“真实版本号”）。
3. **已核对、当前无影响但值得记录**：设置窗口在启动时即由 `tauri.conf.json` 自动创建（`tauri-utils-2.10.0` 的 `WindowConfig.create` 默认为 `true`，见 `tauri/src/app.rs:2691`）。因此 `src-tauri/src/tray.rs:195-213` 的 `WebviewWindowBuilder` 分支与 `created` 标志为不可达代码，其中的尺寸参数不会生效（当前取值与配置一致，无功能影响）；后续若只改一处尺寸常量，两处会静默漂移。
