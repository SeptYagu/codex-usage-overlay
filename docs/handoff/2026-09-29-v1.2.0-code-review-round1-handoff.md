**触发条件**

安装版（`is_installed_version == true`，右栏显示"开机自启动"行）+ 默认 960×620 尺寸下，任一/两个重置提醒的"提示音"下拉选择**自定义音效**（`fiveHourSoundMode` / `weeklySoundMode == 'custom'`，`SoundPicker` 因此渲染；此时甚至尚未选择文件也成立）。语言为 en-US 时**仅一个**自定义音效即触发；zh-CN / zh-Hant 需两个都是自定义音效。

**实际行为与期望行为**

- 期望：默认尺寸下两栏内容完整可见、无垂直滚动条（R-3 明文要求 `clientHeight == scrollHeight`）。
- 实际（headless Chromium 1223 渲染构建产物，视口恰好 960×620 CSS px，Tauri 桥桩提供 `get_settings` / `is_installed_version` / `get_notification_status`；测量值取真实 `getBoundingClientRect`）：

  | 配置 | 根 `clientHeight`/`scrollHeight` | 右栏内容最低点 | 被裁控件（根 padding box 底 = 600px，视口 = 620px） |
  | --- | --- | --- | --- |
  | en-US + 两个自定义音效 | **620 / 691** | 691 | 每周卡"提示音"`<select>` y=589..616（下半 16px 不可见）；路径 `<p>` y=622..646 与 `选择文件…/试听/清除` 三按钮 y=654..680 **完全不可见** |
  | zh-CN + 两个自定义音效 | **620 / 659** | 659 | 路径 `<p>` y=590..614 部分不可见；三按钮 y=622..648 **完全不可见** |
  | zh-Hant + 两个自定义音效 | **620 / 659** | 659 | 同上（三按钮 y=622..648 完全不可见） |
  | en-US + 仅每周自定义 | 620 / 620 | 611 | 无裁切，但右栏内容越过栏底并与 Footer 带（y=571..600）**重叠**（`grid` 自身 `clientHeight 502 / scrollHeight 554`） |
  | en-US / zh-CN 普通（两个都是"Windows 默认"） | 620 / 620 | 559 | 正常，恰好贴合（与方案"仅余约 5px"的自估一致） |

  即：R-3 明文要求的 `clientHeight == scrollHeight` 在"两个自定义音效"配置下为 **620 ≠ 691（en）/ 620 ≠ 659（zh/zh-Hant）**，且由于 `html`/`body`/根三层都是 `overflow: hidden`，用户**看不到任何滚动条**，被裁掉的控件在鼠标操作下不可达（实测：仅在键盘 Tab 聚焦到该按钮时，浏览器会把 `overflow:hidden` 的根容器程序化滚动 39/71px 使其显形——`root.scrollTop` 实测由 0 变为 39/71；此外可手动把窗口拉高，最大 1600px）。
- 期望行为与实际的差距还包括：用户没有任何视觉线索知道"每周提醒的提示音还能选文件"。

**根因**

根容器高度固定为 620，减去 `p-5`（20×2）、header 高 37、footer 高 41、grid 的 `pt-4`（16）后，两栏可用高度恒为 **486px**；而右栏在"两个自定义音效"下的自然内容是 **602~634px**。本次重构把旧根容器的 `overflow-y-auto` 改成 `overflow-hidden`（为满足"零滚动"），同时没有让两栏自身可滚动，也没有压缩右栏内容，于是溢出部分被裁切而不是被滚动或被容纳。方案自估的"右栏约 470px"只在默认（Windows 默认音效）配置下成立，漏算了 `SoundPicker`（路径行 + 3 个按钮 ≈ 72px × 2）。

**影响范围**

设置窗口右栏的每周（en-US 下连 5 小时）重置提醒音频配置：提示音下拉、自定义文件路径、选择/试听/清除三个按钮在默认窗口尺寸下不可见。这是本模块唯一交付的用户界面，且相对旧单栏布局（可滚动）是**功能可达性回归**：此前 480×660 下所有选项都能滚到。受影响的用户是"已选过自定义音效"的存量用户与按设计切换过"自定义音效"的新用户；三语言全部命中。

**修复建议**（按推荐度排序，任选其一即可让内容可达，"零滚动"与"内容不被裁"必须同时满足）

## 三、待确认风险与未验证项

**待确认风险（非已确认缺陷，但建议在下一轮落结论）**

1. **方案 §3.2 散文与实现判据在"≥3 屏且无多数"时不一致（文档未随实现同步）**：`docs/handoff/2026-09-29-tray-menu-width-optimization.md:100`（"若进入目标屏幕 B 的面积 <=50%…判定归属保留在原显示器 A"）与 `src-tauri/src/dock.rs:560-599` 的实测判据（**严格最大面积获胜**，仅并列时才用宿主破平）在"三屏错位、无任何屏 >50%"时给出不同结果（如面积占比 A=16.5 % / B=28.5 % / D=20.2 %、宿主 D：伪代码与实现判 B，散文读法判 D）。**怀疑依据**：round-3 handoff 的 P3-3 正是要求把三处表述统一为"严格最大面积 + 宿主破平"（`docs/handoff/2026-09-29-workbuddy-code-review-round3-handoff.md:151`），本提交按该建议改了**代码**（`select_monitor_by_overlap` 的文档注释自称 "the single authoritative attribution rule"，并有 `the_strictly_largest_share_wins_even_without_a_majority` 断言显式排除散文读法），但**未同步改方案文档** §3.2/§3.3.1。**缺少的证据**：用户对"无屏过半时"归属的期望（§3.1 只约束 >50% ⇒ 目标屏，该条实现严格满足）。**建议**：下一轮把方案 §3.2 情形 B、§3.3.1 注释改写为与实现一致的 totality 契约（一句话），使文档与代码同源；无需改代码。
2. **保护期内的瞬时失焦 + `set_focus` 失败仍会 hide**：`src-tauri/src/tray.rs:141-149` 的守卫是 `pending_blur && !is_focused`（与方案 §2.2.3 ① 一致，属**规定行为**），因此若 Windows 前台锁定使 `set_focus()` 始终失败，且保护期内收到过 transient killfocus，则到期仍会 hide——即模块二要解决的"点击无反应"在极端焦点场景下仍可复现。**怀疑依据**：方案 §2.1 根因 #1 描述的正是"后台进程抢不到前台焦点 + 瞬时失焦"。**缺少的证据**：真机 `Focused(false)` / `is_focused()` 事件序列（无 GUI 无法采集）。**建议的验证方法**：开启鼠标穿透后，在另一个前台窗口保持活动的状态下点击托盘图标，记录弹窗是否稳定可见（≥3 次），并把 `is_focused()` 与 `pending_blur` 的时序打印到日志。

**未验证项（受环境限制）**

- 无 GUI / 多屏实机：多屏拖拽归属与接缝防误折叠的真实几何、越界回弹、托盘点击/双击时序、`set_focus` 的真实成败、以及 R-3 要求的 100/150/200% DPI 截图均未执行（本机单显示器、无 Tauri 运行时）。本轮的替代覆盖是：真实布局引擎（Chromium）验证前端几何与设置窗口高度、隔离沙箱变异验证断言落地性、以及 Rust 纯函数层的行为矩阵。
- 本轮的 P2-1 证据来自 Chromium 的布局引擎（与 Tauri 使用的 WebView2/Chromium 同源）而非 WebView2 本体；字体度量在两端的差异可能使**临界**配置（如 en-US 仅一个自定义音效、越界 11px）在实机上略有出入，但三个"两个自定义音效"配置的溢出量为 39~71px，远超字体差异能吸收的范围。
- 未验证 `SETTINGS_MIN_HEIGHT = 500`（窄栏 + 最小高度）下的可达性：按 P2-1 的同一根因，最小高度下的裁切只会更严重，修复 P2-1 时应一并覆盖。
- `apply_settings_geometry` / `center_settings_window`（`src-tauri/src/tray.rs:514,546`）仍无自动化证据（v1.1.3 以来的既有缺口，见 STATUS R-2），本轮未变更该文件路径的相关逻辑。

**残余风险**

- 模块一/模块四的实机视觉（刻度线在深色模式底槽上的对比度、弹窗在 100/150/200% DPI 下的物理尺寸）只能由实机截图确认；本轮只验证了几何位置、层级与"开启/关闭"两态。
