# Codex Usage Overlay v1.3.1 — Display Controls Plan

Date: 2026-10-03  
Baseline: `7b335d7` (`docs: finalize v1.3.0 changelog`)  
Scope: plan only; no production implementation in this commit.

Revision: addresses the [round-1 design review](2026-10-03-v1.3.1-design-review-round1-handoff.md) at `4cfdd29`. Display controls are required for v1.3.1; the estimator refinement is independently gated and may be deferred.

## 1. Goal

v1.3.1 adds two independent presentation preferences:

1. `showBurnRate` — show/hide the `x%/h` Burn Rate text introduced in v1.3.0.
2. `showFiveHourQuota` — show/hide all user-visible 5-hour quota presentation.

The second control is needed because some account/subscription configurations may not use a meaningful 5-hour quota. The application must therefore be able to present Weekly usage without forcing an irrelevant 5H module.

The required v1.3.1 scope is presentation controls. Phases 2–4 must not change the v1.3.0 sampling, estimator, reset-detection, persistence, or refresh-pipeline semantics.

Phase 5 is a separate, optional estimator refinement. Only that phase may change the published rate formula and add the compatible estimator metadata specified in §8.1.6. It must preserve raw observation handling, account isolation, crossing reconstruction, reset/correction protection, polling cadence, and the refresh pipeline. If its replay gates fail, defer Phase 5 and release the verified display controls with the v1.3.0 estimator unchanged. Sections 13–14 define the two release paths.

## 2. Product decisions

Both new settings default to `true`.

That preserves v1.3.0 display visibility for every existing installation after upgrade. Users opt out only when the extra information is not useful. Rate behavior changes only if the independently validated Phase 5 is included.

`showBurnRate` controls Burn Rate text only. It does not stop BurnRateTracker collection or persistence.

`showFiveHourQuota` controls presentation only. It does not stop fetching 5H data, storing it, estimating its burn rate, or processing reset state.

The two controls are independent:

| showFiveHourQuota | showBurnRate | Expanded overlay |
| --- | --- | --- |
| true | true | 5H + WK; both show countdown and Burn Rate |
| true | false | 5H + WK; countdown only |
| false | true | WK only; WK countdown + Burn Rate |
| false | false | WK only; countdown only |

`showCredits` remains independent from both.

No automatic subscription-tier detection is required in v1.3.1. The user explicitly selects the presentation appropriate to the account.

## 5. Expanded overlay behavior

Build the visible quota list from settings instead of always rendering both quota blocks.

When `showFiveHourQuota=true`:
- render 5H first;
- render WK second.

When `showFiveHourQuota=false`:
- omit the 5H quota block and its divider entirely;
- render WK as the first/only quota block;
- retain normal grouped/stacks behavior.
Burn Rate rendering is conditional inside each visible quota block:

- `showBurnRate=true`: metadata row contains countdown + Burn Rate.
- `showBurnRate=false`: metadata row contains countdown only.

When Burn Rate is hidden, do not leave an empty rate span, placeholder dash, or reserved horizontal gap.

The final overlay width remains content-driven through the existing ResizeObserver path.

Credits behavior is unchanged except that divider placement must still be correct when 5H is absent.

Examples:

```text
5H ON, Rate ON, Credit ON:
5H 90% | WK 80% | CR $...
2h 34m 16.8%/h   4d 02h 0.6%/h

5H OFF, Rate ON, Credit ON:
WK 80% | CR $...
4d 02h 0.6%/h

5H OFF, Rate OFF, Credit OFF:
WK 80%
4d 02h
```

## 6. Collapsed edge pill

`showFiveHourQuota=false` must also remove the 5H bar from the collapsed edge pill.

Current pill rendering always iterates both quotas. v1.3.1 should reuse the same visible-quota list or equivalent visibility helper so expanded and collapsed modes cannot drift.

One-bar pill behavior must be intentional and should become a true **Weekly-only presentation mode**:

- render exactly one Weekly track;
- center the Weekly track within the existing pill host;
- keep the track visually identical in thickness to the current quota bars rather than stretching it merely to fill spare width;
- preserve percentage-grid behavior on the Weekly track;
- preserve top/bottom rotation behavior;
- do not leave an invisible/empty 5H track occupying width;
- update accessible labels so a hidden 5H quota is not still announced by the pill.

Conceptually:

```text
5H visible:     | 5H | WK |
5H hidden:         | WK |
```

The pill host dimensions and docking hit target should remain unchanged unless real-layout verification proves a change is required. The visual content simplifies, but the edge hover/click target should not become unnecessarily smaller.

`showBurnRate` has no collapsed-pill effect because Burn Rate text is not rendered there today.

## 7. Tray tooltip and tray icon

The current tray tooltip mirrors `showCredits`; 5H visibility should follow the same presentation principle.

When `showFiveHourQuota=true`:
- tooltip keeps `5H … | WK …` plus optional Credit.

When `showFiveHourQuota=false`:
- tooltip contains `WK …` plus optional Credit;
- do not render `5H --%` or any other placeholder.

The tray icon currently encodes 5H as the outer ring and Weekly as the inner ring.

When 5H is hidden, switch the icon into a true **Weekly-only single-ring mode**:

- do not draw the 5H outer ring or its inactive track;
- promote Weekly from the small inner ring to one large primary ring using the current outer-ring radius/visual weight;
- the single Weekly ring should use the same quota-health coloring and percentage arc semantics as the normal Weekly ring;
- do not leave an empty outer track around a small inner Weekly ring;
- do not draw two concentric rings when only one quota is being presented.

Conceptually:

```text
5H visible:        outer ring = 5H
                   inner ring = WK

5H hidden:         single large ring = WK
```

This is a presentation remapping only. The underlying Weekly field and semantics do not change.

The tray-icon renderer therefore needs explicit presentation mode rather than overloading `None`. `None` currently means “quota unavailable” and still draws an inactive track, which is different from “this quota is intentionally hidden”.

A small explicit mode is preferable, for example:

```rust
enum TrayQuotaMode {
    FiveHourAndWeekly,
    WeeklyOnly,
}
```

An equivalent boolean-driven implementation is acceptable if the rendering semantics remain equally explicit and testable.

The same tray presentation helper must be used by **every** icon-writing path: startup (`setup_tray`), successful usage refresh (`process_usage_success`), failed usage refresh (`refresh_usage`), and settings changes (`apply_settings_patch`), including `last_usage=None`. Pass the saved/current settings explicitly; unavailable quota values must never select dual-ring mode implicitly.

Treat presentation mode, available usage, and read status as independent inputs. Preserve the initial application-name tooltip before a result and the localized error tooltip after failure; do not replace a current error with a cached-success tooltip merely because visibility changed. Failure continues to draw unavailable quota tracks as today, but in the selected presentation mode. Do not clear cached usage on failure or on display changes.

| Lifecycle state | `showFiveHourQuota=false` icon | Tooltip |
| --- | --- | --- |
| Cold startup before first result | One large inactive Weekly ring | Initial application name |
| Successful result | One large Weekly ring with current percentage/color | WK plus optional Credit |
| Failed result, with or without prior cached usage | One large inactive Weekly ring | Localized read error |
| Display toggle before any result, no cache | Immediately redraw in the selected mode | Keep initial application name |
| Display toggle while in error, with or without cache | Immediately redraw unavailable tracks in the selected mode | Keep localized error, using the current language |
| Display toggle after success | Immediately redraw in the selected mode from cached usage | Recompose cached WK/5H and optional Credit |

The corresponding `true` cases use two quota tracks, including two inactive tracks for startup/error. Weekly-only + Weekly unavailable still means exactly one large inactive Weekly ring.

Changing `showFiveHourQuota` must update the tray presentation immediately, using cached `last_usage` when the read status permits and unavailable values otherwise. It must not wait for the next scheduled usage poll and must not spawn a new Codex network/app-server fetch merely to repaint presentation. Add a small in-memory tray read-status enum (`Pending`, `Success`, `Error`, or equivalent) if the existing state cannot distinguish these cases; it is presentation state and does not change fetching or the usage DTO.

## 8. Data, estimator, and notification independence

Display settings must not mutate underlying quota data.

Turning off either display switch must NOT:
- clear BurnRateTracker history;
- stop Burn Rate persistence;
- skip 5H parsing;
- change polling cadence;
- change `last_usage`;
- alter reset-cycle detection;
- alter account-switch isolation;
- fabricate `None` values in the usage DTO;
- trigger a network refresh merely because a display switch changed.

5-hour reset notification preferences remain independent.

Specifically, `showFiveHourQuota=false` must not implicitly disable `fiveHourResetNotification`. A user may hide the quota while still wanting a reset alert.

Likewise, turning the display back on should immediately reuse current cached data/history rather than needing a new estimator warm-up period.

### 8.1 Burn Rate estimator refinement: exponentially weighted local crossing regression

The v1.3.0 estimator should be refined without discarding its crossing-based architecture.

The new estimator must preserve the most important invariant:

> For a genuinely constant burn rate, recency weighting must not systematically change the answer.

Examples:
- stable `1% / minute` should converge to approximately `60%/h`;
- stable `1% / 2 minutes` should converge to approximately `30%/h`;
- weighting exists to improve response when the rate changes, not to bias a stable rate upward or downward.

#### 8.1.1 Keep crossing reconstruction and protection logic

Continue using the existing:
- validated raw `usedPercent`;
- integer percentage `CrossingEvent` reconstruction;
- interpolation of multiple crossings inside a sampling interval;
- account isolation;
- reset-boundary segmentation;
- correction-candidate handling;
- max-gap segmentation;
- bounded persisted crossing history.

Do not replace this with a moving average of raw per-poll deltas. Poll-frequency-dependent zero samples such as repeated `22% -> 22%` observations must not become ordinary equal-weight rate samples.

#### 8.1.2 Fit a recency-weighted local slope

For eligible crossing events in the current segment, treat:
- `t_i` = crossing time in seconds;
- `L_i` = crossed integer percentage level.

Assign exponential recency weights:

```text
w_i = 2 ^ ( - age_i / half_life )
```

Then fit the weighted least-squares line:

```text
L ~= a + b * t
```

using weighted means and a centered time axis for numerical stability:

```text
b = sum(w_i * (t_i - t_bar) * (L_i - L_bar))
    / sum(w_i * (t_i - t_bar)^2)

burn_rate_per_hour = b * 3600
```

A perfectly linear sequence remains perfectly linear under positive weighting, so a stable `1%/min` sequence remains approximately `60%/h` even though recent crossings receive larger weights.

Keep the 5H 30-minute and Weekly 24-hour hard evidence horizons. The regression may use a shorter local time window within those horizons; define and record that window separately from the hard evidence cutoff and half-life.

The original 5H 5-minute half-life is a **comparison candidate, not an approved default**. Round-1 replay found that after four new crossings its `60 -> 120%/h` estimate was `63.448%/h` versus legacy `102.857%/h`, and its `60 -> 30%/h` estimate was `49.863%/h` versus legacy `25.714%/h`. Giving recent crossings larger weights is not sufficient to beat legacy's recent 2–3-point span.

Replay a parameter grid that includes the original candidate, shorter half-lives, and shorter local windows. Weekly's original 4–6-hour half-life is also unapproved until its own replay passes. Select final parameters using the quantitative gates in §11.6; do not choose a replacement constant from intuition or claim that a shorter half-life necessarily passes. If no candidate passes both stability and response gates, defer Phase 5.

#### 8.1.3 Preserve minimum-evidence gates

Do not publish a rate from insufficient crossing evidence.

Keep equivalent evidence requirements to the current estimator:
- 5H: at least a 2-percentage-point crossing span;
- Weekly: at least a 1-percentage-point crossing span;
- all crossings must belong to the current segment and remain inside the hard evidence horizon.

If the weighted-regression denominator is zero/non-finite, or evidence is insufficient, return unavailable rather than fabricating a rate.

#### 8.1.4 Treat idle time as right-censored evidence, not repeated zero-rate samples

Weighted regression over historical crossings alone cannot detect that consumption has stopped. However, reconstructed crossing times are estimates inside sampling intervals, not exact event times. A single crossing reconstructed at the interval midpoint must not start an exact one-point idle deadline at that midpoint.

For the newest crossing, retain the upper endpoint of its reconstruction interval: the time of the accepted observation that first confirmed that crossing. For a multi-crossing observation, the same confirming observation is the upper bound for all crossings reconstructed in that interval. Keep the existing interpolated timestamps for regression; use this separate conservative upper bound for idle evidence.

Define:
- `r_fit` = eligible weighted-regression rate in `%/h`;
- `crossing_upper_at` = confirming observation time of the newest crossing;
- `end_time` = latest accepted valid observation time;
- `idle_age_min = max(0, end_time - crossing_upper_at)`.

For finite positive `r_fit`, the expected one-point interval is `3600 / r_fit`. While `idle_age_min` is no larger than that interval, apply no new idle cap. Once it exceeds the interval:

```text
idle_cap = 3600 / idle_age_min
candidate = min(r_fit, idle_cap)
idle_rate_ceiling = min(previous_idle_rate_ceiling, candidate)
published_rate = idle_rate_ceiling
```

An absent previous ceiling imposes no restriction. Once an idle ceiling exists, continue taking the minimum with it on later unchanged observations until a new crossing or segment transition clears it. This prevents partial horizon expiry from raising the published rate during uninterrupted idle. Check current-segment evidence and minimum span on every observation first; insufficient/expired evidence returns unavailable rather than preserving the ceiling as a rate. Non-finite/non-positive fits return unavailable without dividing by them.

Unchanged observations must **not** move `crossing_upper_at` forward. Otherwise genuine idle would continually restart the deadline. A valid fractional increase without an integer crossing also does not move it; fractional and quantized traces must both be replayed before publication. Invalid, stale, same-timestamp-conflicting, and pending-correction samples cannot update the upper bound or idle ceiling as accepted observations.

Required round-1 counterexample: observe `(t,usedPercent)=(0,10),(60,11),...,(1800,40)` with constant underlying `1%/min`. The newest reconstructed crossing is at `1770`, but its upper bound is `1800`. A valid unchanged integer observation `(1845,40)` gives `idle_age_min=45s`, so it must retain the `60%/h` fit instead of the former `48%/h` cap. The next real integer crossing may occur at `1860`. For a genuinely stopped trace, later valid unchanged observations eventually exceed the conservative deadline, lower the rate monotonically, and age the evidence out.

This deliberately allows uncertainty-based detection delay of up to the confirming sampling interval. It does not claim exact stop timing from integer observations. Changing polling cadence or inserting a manual refresh must be tested using the same underlying consumption trajectory and varying quantization phase, including cases where reconstructed crossings differ (§11.6). Elapsed accepted time, rather than unchanged-poll count, controls the idle cap.

#### 8.1.5 Gap handling remains separate from user idle

A user pausing between prompts is not a sampling gap if the overlay continues receiving valid unchanged quota observations.

The existing max-gap rule applies only when valid quota observations themselves are missing.

Retain the existing 5H 10-minute and Weekly 6-hour max-gap constants for this release. Do not introduce the former 3–5-minute fixed threshold candidate: the UI supports 300-second polling, and the polling loop sleeps after each completed fetch, so normal accepted observations can be separated by 300 seconds plus request duration. A 300-second threshold can repeatedly clear healthy history.

Replay all UI cadences (30/60/120/300 seconds) with successful-fetch durations and scheduling jitter, as well as truly missing observations. The patch allowlist also accepts 15–3600 seconds; include those boundaries and document the inherited behavior that a configured cadence longer than the fixed 5H max-gap yields segmented/unavailable 5H evidence. Do not silently change that policy in Phase 5. A future max-gap change requires a separate cadence-aware contract and failure/recovery evidence; it must not assume that every user polls once per minute.

#### 8.1.6 Migration and implementation strategy

Reuse the existing persisted `CrossingEvent` history; do not clear it or require new crossing warm-up solely because the formula changed. Phase 5 adds two per-quota fields to `QuotaRateState`, each with a missing-field default of `None`:

```rust
last_crossing_observation_at: Option<i64>,
idle_rate_ceiling: Option<f64>,
```

Persist the upper bound so restarting cannot turn it into the old interpolated midpoint. When an accepted interval creates crossings, set `last_crossing_observation_at` to that interval's observation time and clear `idle_rate_ceiling`. Clear both on segment/reset/account transitions. During idle, update the ceiling according to §8.1.4 and preserve the upper bound. Save with the existing atomic state-write path; no separate file or changed crossing-event format is needed.

For a legacy state file with current-segment crossings but no upper bound, adopt its stored `last_observed_at` once as a conservative upper bound before processing new observations. This may delay idle detection, but does not change stored crossings or regression availability. Do not adopt every new unchanged observation as a replacement bound. If a valid bound already exists, preserve it on load. Validate that the bound is between the newest crossing time and stored last observation, and that a loaded ceiling is finite and positive. A malformed upper bound uses the conservative fallback and clears the ceiling; a malformed ceiling alone is discarded without changing a valid upper bound. Deserialize these optional fields defensively (for example, a field-level tolerant deserializer before semantic validation), so wrong JSON types cannot make the entire otherwise-valid state file fail to load. Do not discard valid crossing history because an optional field is absent or malformed.

Keep the state schema compatible with the existing serde missing-field defaults and test old/new serialization. If Phase 5 is deferred, none of these metadata changes enter the v1.3.1 production state model; display controls retain v1.3.0 persistence behavior.

Mark metadata normalization/migration as a state change and persist it through the existing checked save path at load or with the next accepted observation, including an unchanged observation. Save the migrated bound before advancing the stored observation baseline, so repeated restart cannot migrate from an ever-later timestamp. Report write failures through the existing persistence-error path rather than claiming restart preservation when saving failed.

Implementation should be staged:
1. extract the current estimator as an explicit legacy/reference function;
2. implement the weighted local-regression estimator against the same crossing state;
3. replay deterministic synthetic traces through both estimators;
4. tune half-life/local-window parameters while retaining current max-gap constants;
5. replace the published estimator only after invariants and response tests pass;
6. remove or retain the legacy estimator only after the comparison fixtures no longer need it.

This estimator refinement is logically independent from the two display switches. Keep it in a separately reviewable change; if its gates fail, exclude it from release code and defer it to a later release. Do not ship an unvalidated estimator behind either display preference.

### 11.6 Burn Rate estimator replay and invariants

These gates are required only if Phase 5 is included. Add deterministic Rust replay fixtures covering the complete raw-observation acceptance/reconstruction path and both the legacy/reference estimator and the weighted estimator; injecting ideal crossing points alone is insufficient.

Required invariants:
- constant `1%/min` converges to approximately `60%/h`;
- constant `1%/2min` converges to approximately `30%/h`;
- constant-rate results remain materially unchanged under the same underlying consumption trajectory when observation cadence/phase changes, even if reconstructed crossings differ;
- recent acceleration moves the weighted estimate toward the new faster rate sooner than the legacy estimator;
- recent deceleration moves the weighted estimate toward the new slower rate sooner than the legacy estimator;
- the §8.1.4 round-1 trajectory and inserted `(1845,40)` observation retain approximately `60%/h`, not `48%/h`;
- phase-shifted unchanged/manual observations before the uncertainty-adjusted deadline do not trigger an idle cap;
- once conservative no-crossing evidence exceeds the expected interval, idle lowers the rate monotonically, including when part of the old evidence expires;
- continued valid unchanged observations eventually age all crossing evidence out and return unavailable;
- missing observations exercise max-gap segmentation rather than masquerading as user idle;
- reset, correction-candidate, invalid-data, account-switch, and persistence behavior remain unchanged;
- the weighted fit never publishes NaN, infinity, or a negative rate.

Include 30/60/120/300-second observation cadences, successful-fetch durations of 0/5/20 seconds, deterministic scheduling jitter up to 5 seconds, phase offsets, inserted manual observations, and fractional/quantized input. Keep reset boundaries beyond each synthetic trace and consumption within 0–100%. Exercise truly missing observations separately, plus the inherited 15/3600-second configuration boundaries from §8.1.5.

Quantitative publication gates:
- Pure linear-crossing WLS fixtures preserve the exact constant slope within relative tolerance `1e-9` (before display rounding).
- For raw constant `60%/h` and `30%/h` fixtures, after warm-up with at least eight eligible crossings spanning seven points, all available outputs remain within 5% of the underlying rate across the cadence/phase matrix. Cases lacking enough evidence are explicitly unavailable, never converted to zero.
- Replay the review's 30-minute `60%/h` history followed by `120%/h` and `30%/h`, plus corresponding Weekly traces scaled to its horizon/cadence. Compare both algorithms at identical accepted observation times. Within the first six new crossings, the candidate's time-weighted absolute error integral must be at least 10% lower than legacy's **for each direction and quota**, not just averaged across fixtures.
- Compute that integral from the rate-change time through the observation confirming the sixth new crossing, holding each algorithm's published rate until its next accepted observation: `sum(abs(rate_j - target) * (t_next - t_j))`. Use the same interval boundaries and include the value already published at the change time. Candidate unavailability at a comparison point where legacy is available fails this response gate; it must not be omitted from the error table to improve the score.
- Report first entry and sustained entry (three consecutive available observations) into a ±10% target band, in seconds. If both estimators sustain the band in the trace, the candidate must do so no later; if legacy never reaches it, report that explicitly rather than inventing a finite legacy time. Extend each trace long enough to establish candidate settling, without crossing a reset or 100% saturation.
- Outside the range bounded by the old/new target rates, candidate transient overshoot/undershoot may not exceed legacy's maximum excursion on the same trace. A candidate cannot pass by exchanging faster response for worse excursions or systematic constant-rate bias.

Record per-fixture availability, errors, response times, excursions, and the selected half-life/local-window parameters. The review's slower 5-minute candidate remains a negative comparison fixture. Failure of any publication gate defers Phase 5; it does not block a verified display-only release.

Persistence/idle fixtures must cover legacy-state load without the two new fields, unchanged observations after load, save/reload during idle, preservation of an existing bound/ceiling, malformed optional metadata, new-crossing clearing, and reset/account/max-gap clearing. Check that repeated restart or unchanged polls do not continually advance the idle bound, and that migration preserves regression availability without new crossing warm-up.

## 14. Acceptance criteria

v1.3.1's required display scope is complete when:

- two persisted switches exist: 5H visibility and Burn Rate visibility;
- both default true for fresh and upgraded installations;
- disabling Burn Rate removes rate text without stopping estimator collection;
- disabling 5H removes every visible 5H representation from expanded overlay, collapsed pill, tray tooltip, and tray icon;
- the collapsed pill becomes one centered Weekly progress bar;
- the tray icon becomes one large Weekly ring rather than a small inner ring with an empty outer track;
- that tray mode also holds during cold startup, read failure/recovery, and settings changes without cache, with unavailable Weekly rendered as one large inactive ring;
- Weekly remains fully usable when 5H is hidden;
- Credit remains independent;
- 5H notifications remain independent;
- toggling visibility does not clear history or require Burn Rate re-warm-up;
- no orphan dividers, empty gaps, clipping, or hover-loss regressions occur;
- dock geometry responds immediately to either display change;
- all frontend/Rust/build/check gates pass;
- supported languages, layouts, scales, and DPI combinations pass real-machine verification.

If Phase 5 is included, additionally require:
- constant-rate and cadence/phase invariance within §11.6 tolerances, including the round-1 manual-refresh counterexample;
- both acceleration and deceleration pass the per-quota quantitative response/error/excursion gates;
- idle caps use the confirming-observation upper bound, lower monotonically during genuine idle, and eventually age to unavailable;
- compatible metadata migration and restart behavior pass without clearing crossing history or forcing warm-up;
- selected parameters and replay results are documented.

If Phase 5 is deferred, completion instead requires an unchanged production v1.3.0 estimator/state format and an explicit deferral record. Missing estimator-improvement evidence is not a claim of algorithm success and does not block the required display scope.

## 15. Out of scope

Do not add in v1.3.1:
- automatic subscription-tier detection;
- automatic hiding based on missing quota data;
- a switch that disables BurnRateTracker computation;
- a switch that disables 5H network parsing;
- replacing crossing reconstruction with raw per-poll delta averaging;
- poll-frequency-dependent zero-rate samples;
- token/s or inference-speed metrics;
- new quota types;
- persistent app-server work;
- analytics/history UI.

## 16. Version rationale

`1.3.1` covers the required display controls. A fully validated estimator refinement may accompany them as a quality improvement to the existing metric. Keep the display and estimator changes separately reviewable. Failure to validate the optional refinement means publishing the verified display-only path and scheduling the estimator for a later release; it does not justify weakening the numerical gates.
