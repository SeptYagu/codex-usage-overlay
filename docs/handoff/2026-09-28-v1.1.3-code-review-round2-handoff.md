## 二、审查发现与缺陷清单

### P2-1 / CR2-1 从托盘退出时若设置窗口处于最小化状态，会把已保存的有效几何覆盖为 0×0 的无效记录（跨会话几何记忆被清空，相对 Round 1 的回归）

**文件与行号**
- 兜底落盘入口：`src-tauri/src/lib.rs:253-266`（`RunEvent::Exit`，守卫只有 `window.is_visible()`）
- 落盘函数：`src-tauri/src/lib.rs:286-297`（`persist_settings_geometry` 只校验 `scale`，不校验尺寸）
- 写入：`src-tauri/src/config.rs:232-240`（`save_settings_geometry`，无条件覆盖旧文件）
- 读取校验：`src-tauri/src/config.rs:212-218`（要求 `width > 0 && height > 0`，故 0 尺寸记录会被判为损坏）
- 恢复兜底：`src-tauri/src/tray.rs:243-250` → `src-tauri/src/tray.rs:259-262`（`None` → `center_settings_window` 居中 480×660）

**触发条件**
打开设置窗口 → 移动/缩放 → 点击标题栏最小化 → 从托盘菜单选“退出悬浮窗”（`exit_app` → `app.exit(0)`）或系统关机 → 重启 → 从托盘打开设置。

**实际行为 vs 期望行为**
- 实际：`RunEvent::Exit` 的 `is_visible()` 守卫对最小化窗口返回 `true`，于是执行落盘；此刻 `inner_size()` 为 `0×0`，`persist_settings_geometry` 通过 `scale` 校验后写出 `{"x":0.0,"y":1341.0,"width":0.0,"height":0.0,"scale_factor":1.0}`，**覆盖掉上一份有效记录**；下次打开时 `load_settings_geometry` 因 `width > 0` 不成立返回 `None`，窗口退化为居中 480×660。
- 期望：最小化不应销毁已持久化的几何；“调整后直接退出”路径应保留用户最后一次非最小化的位置与尺寸。
- 相对 Round 1 的差异：`1e363b6` 仅有 `CloseRequested` 一条落盘路径，最小化后退出不会写文件、有效记录得以保留；`ba81595` 新增的退出兜底把该记录改写成无效值 ⟹ **本项为本轮修复引入的回归**。

**根因**
1. `IsWindowVisible` 对最小化窗口仍返回 `TRUE`（`WS_VISIBLE` 未清除），因此 `is_visible()` 守卫无法排除最小化状态。
2. 最小化时 `GetClientRect` 返回 `0×0`，而 tao 0.37.1 的 `inner_size()` 正是 `GetClientRect`（`src/platform_impl/windows/window.rs:219-225` 调用 `util::client_rect`），故 `inner_size()` = `0×0`。
3. `persist_settings_geometry` 仅校验 `scale.is_finite() && scale > 0.0`（`lib.rs:287`），未校验 `size.width/height > 0`，于是把 0 尺寸当作有效值写入。
4. `save_settings_geometry` 无条件 `tmp`+`rename` 覆盖旧文件，导致有效记录不可恢复。

**复现方法 / 运行证据**
1. 原生探针（临时程序 `/d/tmp/geom-probe/winmin.rs`，已删除，未入库）：`CreateWindowExW` 创建离屏、`WS_EX_TOOLWINDOW`（不占任务栏）的 `WS_OVERLAPPEDWINDOW`，依次 `ShowWindow(SW_SHOWNOACTIVATE)` / `SW_MINIMIZE` / `SW_RESTORE`，读 `IsWindowVisible`/`IsIconic`/`GetWindowRect`/`GetClientRect`，结果：
   - `created(never shown): visible=false iconic=false outer=(30000,30000,30480,30660) client=464x621`
   - `shown offscreen:     visible=true  iconic=false outer=(30000,30000,30480,30660) client=464x621`
   - `minimized:           visible=true  iconic=true  outer=(0,1341,237,1380)         client=0x0` ← 守卫通过且尺寸为 0
   - `restored:            visible=true  iconic=false outer=(30000,30000,30480,30660) client=464x621`
2. tao 0.37.1 源码：`is_visible()` = `util::is_visible`（`window.rs:628-630`）、`outer_position()` = `GetWindowRect`（`window.rs:177-181`）、`inner_size()` = `client_rect`（`window.rs:219-225`），三者均未对最小化状态做特殊处理。
3. `minimizable` 默认 `true`（`tauri-utils-2.10.0/src/config.rs:2421`），且 `tauri.conf.json` 中设置窗口为 `decorations: true` ⟹ 标题栏存在最小化按钮，触发路径在正常 UI 下可达。
4. `exit_app` = `shutdown_audio` + `app.exit(0)`（`src-tauri/src/commands.rs:546-550`），`app.exit(0)` 会触发 `RunEvent::Exit`，路径可达。

**影响范围**
本版本核心交付（窗口几何跨会话记忆）在“最小化后退出”这一路径上静默失效，且会**销毁此前已保存的有效几何**；窗口退化为主屏居中 480×660（不会崩溃、不会产生幽灵窗口）。同一隐患也存在于 `CloseRequested` 路径（最小化窗口被任务栏“关闭窗口”/Alt+F4 关闭时：`lib.rs:55-64` 走同一个 `persist_settings_geometry`），只是概率远低于退出路径。

**修复建议**
- 首选在 `persist_settings_geometry` 内加固：`if let (Ok(position), Ok(size)) = (position, size)` 之后追加 `if size.width == 0 || size.height == 0 { return; }`（或要求 `size.width > 0 && size.height > 0`），一处修复覆盖 `CloseRequested` 与 `RunEvent::Exit` 两条路径。
- 可选叠加：`RunEvent::Exit` 的守卫改为 `if window.is_visible().unwrap_or(false) && !window.is_minimized().unwrap_or(false)`。
- 不建议只改退出路径——那会留下 `CloseRequested` 的同类漏洞。

**修复后验收标准**
1. 打开设置 → 移动/缩放 → 最小化 → 托盘退出 → 重启 → 打开设置：恢复到最小化前的物理位置与逻辑尺寸；`%LOCALAPPDATA%\CodexUsageOverlay\settings-window-geometry.json` 在退出前后保持为有效的非零记录。
2. 对最小化的设置窗口执行任务栏“关闭窗口”后重启：同样复原，不写入 0 尺寸记录。
3. 既有行为不回归：正常关闭（X）后重启仍精确复原；`RunEvent::Exit` 仍能兜底保存“调整后直接退出”的场景。
4. 工作区无 `*.json.tmp` 残留。

### P3-1 / CR2-2 托盘菜单宽度自适应用例使用恒定 `scrollWidth` mock，只覆盖到 300 下限，无法证伪自适应逻辑

**文件与行号**
- `src/components/TrayMenuView.test.tsx:30-32`（`vi.spyOn(Element.prototype, 'scrollWidth', 'get').mockReturnValue(280)`）
- `src/components/TrayMenuView.test.tsx:40-62`（用例 `remeasures tray content when the language list opens and closes`，三处断言期望 `widthLogical: 300`）

**触发条件**
任何使“测量宽度聚合 / `+20` 内边距 / `clamp(TRAY_MENU_MIN_WIDTH, TRAY_MENU_MAX_WIDTH)`”失效的改动（例如误把 `item.scrollWidth` 换成 `clientWidth`、漏掉 `.tray-menu-item` 遍历、写错 clamp 边界）。

**实际行为 vs 期望行为**
- 实际：mock 对**所有**元素恒定返回 `280`，因此 `intrinsicWidth` 恒为 `280`、`width` 恒为 `300`（恰好等于 `TRAY_MENU_MIN_WIDTH`）；三个 revision 的断言都只验证“恒为 300 下限”，即使宽度聚合与 clamp 逻辑被整体删除/写错，用例仍会通过（`heightLogical` 断言不受影响，故不会连带失败）。
- 期望：至少有一条用例让“测量宽度 > 下限”，断言更大的 `widthLogical`（并覆盖 500 上限的 clamp 行为），使 `TrayMenuView.tsx:55-59` 的聚合与 clamp 逻辑可被证伪。

**根因**
mock 返回的是固定常量且小于自适应阈值，等价于只测了“最小宽度地板”，未测“自适应”这一本轮新增能力（属评审规则中的“无效 mock / 功能无效仍可通过”）。

**影响范围**
仅测试有效性，非产品缺陷：本轮已在真实 Chromium 中独立验证生产路径确实生效（长文案 `content.scrollWidth=377`、`item.scrollWidth=377`，短文案均为 280），故当前无可见功能缺失；风险在于后续若有人改坏该逻辑，测试不会报警。

**修复建议**
新增一条用例：把 `scrollWidth` mock 提高到超过下限（如 `420`），断言 `widthLogical: 440`；再用 `>500` 的值（如 `600`）断言被 clamp 到 `500`。

**修复后验收标准**
把 `TrayMenuView.tsx` 的 `Math.max(content.scrollWidth, item.scrollWidth)` 聚合或 `clamp` 边界任一处改错时，新用例必须失败。
