## 2. 逐项实施

### 2.1 [High] `audit_outbox` 刷盘后未落盘清空

- `BurnRateTracker::flush_audit_outbox` 在清空槽位后置 `state_dirty = true`。
- `refresh_usage` 在第二次 `flush_audit_outbox` 之后，若 `tracker.is_dirty()` 立即再写一次状态文件；写失败时 `state_dirty` 保持为真，下一次刷新继续重试。
- `BurnRateTracker::load` 在启动刷盘成功后，同样把清空后的槽位写回 `burn-rate-state.json`。
- 结果：事件只会被追加一次，跨重启不再重复追加。

### 2.2 [High] `audit_busy` 期间 `pending` 对失效信号失明

- `PendingPersonalForecast` 新增 `origin_segment_id`（区间创建时的分段身份）与 `latched_rejection`（已锁定的拒绝决定）。
- `audit_busy` 为真时不再整体跳过 `pending`：
  - 本拍出现分段切换 → 按切换原因锁定拒绝；
  - 分段身份与 `origin_segment_id` 不一致 → 锁定 `SegmentReset`；
  - `pending.observe` 返回拒绝 → 锁定该拒绝原因；
  - `Continue` → 正常推进 `last_valid_at` / `last_valid_used_percent`；
  - `Matured` → **不**更新学习器、**不**覆盖 `audit_outbox`，区间保持原状待下一拍。
- 锁定一旦写入就不会被后续采样"洗白"。
- `audit_busy` 解除后，锁定的拒绝立即弹出为 `Rejected` 证据事件，区间清空。
- 证据事件记录的是**触发违规的那一拍**（`observed_at` / `target_used` / `actual_gap`），而不是上报它的那一拍。

### 2.3 [Medium] `PendingPersonalForecast` 的反序列化边界

- 新增 `PendingPersonalForecast::is_valid_for(&QuotaRateState)`，覆盖方案 §2.3.1 列出的全部字段：百分比区间、末次有效值不早于原点且小于 100、重置时间戳为正、Fixed Weighted 速率为正、已发布速率与个性化速率的有限性与符号、学习器快照四个字段的有限性与值域、分段身份一致、生产观测时间不早于区间。
- 任一条件不满足时 `FiveHourShadowState::normalize` 置 `pending = None` 并返回 `changed = true`。

### 2.4 [Medium] 无活跃会话时对同一管道重复握手

- `deliver_batch` 维护 `exhausted_pipes`（管道路径小写去重）。
- 管道返回 `Ok(Handshake::NoActiveSession)` 时记入该集合，其余 `caller_thread_id` 的同一管道候选直接跳过；返回 `Err` 时不记入，保留"该 caller 可能不被识别"的回退行为。
- 结果：2 管道 × 3 caller 身份 = 6 个候选，只产生 2 次握手。

### 2.5 [Low] 开关关闭或额度回升时未清理 `periods`

- `AutoPauseController::clear_active_periods()` 清空 `periods`，但**不**重置 `period_counter`（计数器单调递增），也**不**清理 `sent` 去重台账。
- `schedule` 在 `!auto_pause_on_low_quota` 与 `triggered_quotas().is_empty()` 两条提前返回路径上调用它。
- `apply_settings_patch` 在开关由开变关时调用它。
- 结果：会话在"暂停变空闲 → 开关关闭期间重新激活 → 开关重开"之后拿到新的 `#pN` 周期号，重新收到暂停请求。

### 2.6 [Low] 配额充足时 Bridge 状态长期为 `Unknown`

- `PauseControlManager` 增加只读探测 `probe_bridge_status` → `probe_bridge`：仅执行 `list_threads` 握手，**不**调用 `send_message_to_thread`。
- 触发时机：`schedule` 中开关为开、无额度触发且状态仍为 `Unknown`；`apply_settings_patch` 中开关由关变开。
- 探测在后台运行（`spawn_probe`），不阻塞刷新路径。
- 结果：`get_auto_pause_status` 不再长期返回 `Unknown`，而是真实的 `Available` / `Unavailable`。

## 3. 与方案的差异（逐条说明原因）

方案文档按"目标契约"书写，落地时以下 7 处与仓库实际代码不同。实现以仓库实际代码为准，语义与方案一致：

1. **证据行数计数器**：方案 §2.1.2.1 写的是 `five_hour_shadow.evidence_lines`，实际代码里这个计数器是 tracker 上的 `evidence_lines: usize`，影子状态树里没有该字段。因此只补了 `state_dirty = true`。
2. **启动路径的保存条件**：方案 §2.1.2.3 写的是"把 `if changed` 改为 `if changed || tracker.is_dirty()`"，但实际的 `BurnRateTracker::load` 里**根本没有**这个保存分支——启动路径从来不写状态。实现改为"刷盘消费了事件就把清空后的槽位写回"。
3. **枚举与变体名**：方案 §2.2 用 `ShadowRejectReason::SegmentReset`，实际枚举是 `RejectionReason`（无该变体）。已新增 `RejectionReason::SegmentReset`，稳定证据码 `segment_reset`，并给它补了 serde 派生（`snake_case`，与 `code()` 的字符串一一对应）。
4. **分段失效的原因码**：方案写的是"无论本拍是否出现 transition，跨分段一律映射为 `SegmentReset`"。实现保留了 v1.3.2 的稳定原因码：**本拍带 transition 时用 transition 的具体原因**（`quota_cycle` / `long_idle` / `correction`），只有在分段变了却没有 transition 信号时才用 `segment_reset`。这样证据日志里已有的历史码不会因为这次修复而改变含义。
5. **§2.3 的时间一致性条件**：方案 §2.3.1 给的是 `quota.last_observed_at < pending.last_valid_at`，而 §3.1 的测试文字写成了 `!= Some(pending.last_valid_at)`。后者会把"生产观测比区间更新"的每一个区间都判废，实现采用了 §2.3.1 的精确条件。另外，带有锁定拒绝的区间豁免分段检查——它的拒绝还没上报，不能被丢掉。
6. **Bridge 连接的枚举名**：方案写 `BridgeConnection::Connected`，实际枚举是 `Available` / `Unavailable` / `Unknown`。
7. **回放门禁命令**：方案写 `npm run check:replay-evidence`，仓库里没有这个 npm 脚本。真实门禁是 `node scripts/check-replay-evidence.mjs`（13 份证据文件字节级比对）。

## 4. 一处行为变更（已同步既有测试）

方案 §2.2.2 明确要求：`audit_busy` 期间，若 `PendingOutcome::Continue` 且未满 300 秒，**正常推进** `pending.last_valid_at` 与 `last_valid_used_percent`。这与 v1.3.2 "审计槽位占用时个人状态整体暂停"的旧契约不同。

- **变更后**：审计槽位占用时，区间**继续推进**（保持因果时间线连续），但**不结算**（不更新学习器、不覆盖 `audit_outbox`）。一个繁忙的审计槽位不再白白吃掉一个真实产生的学习区间。
- **既有测试同步**：`commands::shadow_refresh_tests::a_retained_audit_event_is_flushed_before_the_next_sample_is_processed` 原先断言"占用期间区间不推进"（`lastValidAt == 1480`），现按方案改为 `lastValidAt == 1520`，并追加"学习计数器不动"的断言。其余 291 项 Rust 测试未受影响。

## 8. 未验证项（如实标注）

1. **打包与真机原生冒烟未做**：本机无法安装签名包并观察真实重启，因此"跨重启后事件不重复追加""开关关闭再打开后会话被再次暂停""Bridge 状态在真实客户端上变为 Available"这三条只有自动化测试覆盖，没有真机证据。
2. **Bridge 状态徽章前端未渲染**：设置页目前没有渲染 `get_auto_pause_status` 的连接状态。本次修复让后端返回真实状态，但界面上看不到变化（这与本项目"影子阶段不改变用户可见行为"的立场一致）。
3. **`segment_reset` 是新的证据码**：它只在新发现象里出现，尚未进入任何离线分析；后续分析脚本需要认识它。
4. **方案 §2.6 的"数毫秒内可见"** 在真机上不成立：真实管道的握手往返由客户端决定，本次只保证状态不再永久停留在 `Unknown`。
