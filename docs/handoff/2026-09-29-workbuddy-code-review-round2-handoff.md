## 二、审查发现与缺陷清单

### P3-1 保护期到期裁决的条件未唯一化 —— "到期仍未获焦即 hide" 与 "仅 `pending_blur` 为真才裁决" 两种读法行为相反，§7.2.6 的两条断言对两种读法都通过

**文件与行号**

- 方案：`docs/handoff/2026-09-29-tray-menu-width-optimization.md:61-64`（§2.2.3 三个要点）、`:321`（§六 `lib.rs` 行"保护期到期时复检 `!window.is_focused()`，唯有确认仍未获焦时才执行 `hide()`"）、`:368-370`（§7.2.6 两条断言）
- 对应代码：`src-tauri/src/lib.rs:88-90`（唯一 hide 出口）、`src-tauri/src/tray.rs:181-182`（`window.show()` + `set_focus()`，计时起点）

**触发条件**

菜单 show 成功、但系统因 Foreground Activation Lock 未把前台焦点授予 `tray-menu`（即模块二 §2.1.1 要修的核心场景），且保护期内**没有**产生 `Focused(false)`（或产生后已被保护期过滤）。保护期到期。

**实际行为与期望行为**

- 期望（本轮意图）：失焦保护期的裁决以 `pending_blur` 为前置条件 —— 只有"保护期内收到过 `Focused(false)`"才允许在到期时补判隐藏；未获焦但从未收到失焦事件的序列必须保持可见（否则模块二的核心收益归零）。
- 实际（按 `:63-64` 字面实现）：到期定时器无条件检查 `!window.is_focused()`，未获焦即 `hide()`。此时菜单在 show 后 150~200ms 内被自行隐藏 —— 与 round 1 指出的"肉眼表现为毫无反应"是同一现象，只是把触发者从瞬时 killfocus 换成了到期定时器。
- 两种读法在方案里都被 `:63-64` 的措辞容纳（"检查 `is_focused()`…若仍未获焦…则立即执行 `hide()`" 未写 `pending_blur` 门），而 `:369-370` 的两条断言（"grace 内失焦且到期未获焦 ⇒ 隐藏"、"到期已获焦 ⇒ 不展示"）在两种读法下**均通过**，故任何一方实现都能保持测试全绿。

**根因**

方案的到期复检只定义了"到期 → 看 `is_focused()`"这条边，没有把 `pending_blur` 写成该转移的守卫条件；§7.2.6 缺少"无失焦事件 + 到期未获焦"这第三条用例，使守卫条件不可证伪。

**影响范围**

模块二的核心修复（托盘菜单在穿透/后台激活受限时可见且可用）在新实现下可能原样复发；反之，若按守卫读法实现而守卫写错（例如把守卫写成 `blur_seen_ever` 而非"保护期内"），则会退回 round 1 的"常置顶滞留"。两条都是用户可感知路径，且都无测试拦截。

**复现方法或验证证据**

代码路径推演（不依赖运行态）：`lib.rs:88-90` 是 `tray-menu` 的唯一 hide 出口；`:63-64` 的无守卫读法在该出口上新增了一条"定时器主动 hide"的边，其触发条件 `!is_focused()` 恰好覆盖模块二自身声明的激活受限场景。反证测试缺口：把 `:369-370` 两条断言逐字实现，无论守卫是否存在都成立 —— 二者均只断言"有失焦事件"的序列，从未构造"无失焦事件的未获焦序列"。

**修复建议**

1. 在 §2.2.3 把过期裁决的唯一契约写成一行：`grace 到期时，仅当 pending_blur == true && !window.is_focused() ⇒ hide()`；未收到 `Focused(false)` 时到期只清除计时状态、不得 hide。
2. §7.2.6 增第三条可失败断言：`show 成功 → 期间无 Focused(false) → 到期时 is_focused() == false ⇒ 菜单保持可见`（并标注：无守卫实现时必须转红）。
3. 状态机侧注明"`Focused(false)` 是保护期内 hide 的必要条件"，与时序起点（`tray.rs:181` 之后）一并作为该模块的两条不变量。

**修复后的验收标准**

- 三条断言齐备且方向互斥：① grace 内失焦 + 到期未获焦 ⇒ 隐藏；② 到期已获焦 ⇒ 不隐藏；③ **无失焦事件 + 到期未获焦 ⇒ 不隐藏**。
- 把守卫删掉（变成无条件 `!is_focused() ⇒ hide`）后断言 ③ 转红，否则视为未闭环。

### P3-2 模块一的验收仍以旧度量 `scrollWidth` 表述，且没有一条断言能区分 `+40` 与 `+20` —— 固定点回归与"少 20px"两种错误都不会转红

**文件与行号**

- 方案：`:340-342`（§7.1.1）、`:343-344`（§7.1.2"当菜单项出现超长版本号文案（如 `scrollWidth = 360px`）时，自适应撑开至贴合净宽"）、`:20-26`（§1.2 唯一度量 `textW` 与唯一公式）、`:316-317`（§六 测试行）
- 现有实现与被弃用度量：`src/components/TrayMenuView.tsx:58-68`（`+20` 为外层 `p-2.5`；聚合 `item.scrollWidth`）、既有测试 `src/components/TrayMenuView.test.tsx:34-38`、`:76`、`:88`（以 `itemScrollWidth` mock 度量）

**触发条件**

按 §7.1 实现（或更新）模块一测试时。任何一次测量路径都会走到该断言。

**实际行为与期望行为**

- 期望（round 1 验收 #2）：方案给出唯一公式**且**给出精确数值断言，使"把 `+40` 改为 `+20`"或"退回 `scrollWidth` 度量"必然让测试转红。
- 实际：§7.1.1 选用的输入恰好在不可区分点上，§7.1.2 只给"贴合净宽"而不给期望数值，且其输入仍写作 `scrollWidth` —— 而 §1.2 刚刚把 `scrollWidth`（容器耦合、`width:100%` 导致的自引用）判为必须弃用的度量。三者叠加后，两种错误实现的期望值都能自圆其说。

**根因**

验收用例的**输入度量**与 §1.2 钉死的唯一度量 `textW` 不一致（沿用旧 `scrollWidth`），且未补足以 `textW` 表述的精确期望值，故 §7.1 不构成对唯一公式的可证伪检验。

**影响范围**

模块一的核心契约（单行不折行、无 20px 缺口、可收窄）。若按 `+20` 实现，长文案（`检查更新 (当前版本: v1.2.0)`、语言子菜单标签）在最外层各差 20px，横向被裁切且不折行（外层为 `overflow-y-auto`）；若按 `scrollWidth+40` 实现，则 round 1 指认的自引用固定点原样复发。两种都是本模块最核心的可感知回归。

**复现方法或验证证据**

独立边界脚本（本机执行，临时文件已删除）：

```
--- A. 公式 (+40) 与两种错误度量 ---
textW=220: +40=280  +20=280  itemScrollWidth+40=280      <- §7.1.1 的输入落到三者同值点
textW=240: +40=280  +20=280  itemScrollWidth+40=300
textW=260: +40=300  +20=280  itemScrollWidth+40=320      <- textW>=260 才可区分
textW=340: +40=380  +20=360  itemScrollWidth+40=400
--- B. 以 §7.1.2 的输入（item scrollWidth = 360）计算 ---
把 scrollWidth 当 textW : 400
textW = scrollWidth-20   : 380   <- 契约正确值
误用 +20                 : 360
--- D. 旧算法的固定点（本模块要修的病）---
textW=196、初值 500：500 -> 500 -> 500 -> 500（只增不减）
```

结论：① §7.1.1 的 `220 → 280` 在 `+40`/`+20` 下同值，不具区分力；② §7.1.2 的 `360` 具备三种都"贴合净宽"的读法（360/380/400），实现者可任选其一并通过；③ 旧固定点仍可由脚本复现，说明"能收窄"这条不变量必须由用例钉死（§7.1.1 第二句已列，方向正确，但不足以覆盖 `+20` 回归）。

**修复建议**

1. §7.1.2 改为以 `textW` 表述并给出精确期望：`textW = 340 ⇒ widthLogical = 380`（并在测试中注明"预期值 = textW + 40，非 `scrollWidth + 40`"）。
2. 补一条能区分 `+20` 的断言（任意 `textW ∈ [260, 460]`，如 `textW = 260 ⇒ 300`）。
3. 明确新度量在 jsdom 下的替身策略（`Range.getBoundingClientRect()` 探针或"显式注入 `textW`"），避免实现者因无法测量而退回 `scrollWidth`。
4. §7.1.1 用例保留（下限生效），但不得作为唯一数值断言。

**修复后的验收标准**

- `textW = 340 ⇒ 380` 与 `textW = 260 ⇒ 300` 两条精确断言存在；`textW = 220 ⇒ 280` 保留为下限断言。
- 把公式改成 `+20`、或把度量改回 `item.scrollWidth + 40` 时，至少一条断言转红。

1. §7.2.1 增一句：断言经 `apply_settings_patch` 后内存设置 `show_percentage_grid == true`、`revision` 递增，且重新 `load_settings()` 的 JSON 含该键（可复用 v1.1.3 round 5 引入的 `AppState::for_test`，见 `commands.rs:47-75`）。
2. §7.2.7 明确为"含该键 ⇒ 读出 `true`；缺该键 ⇒ 读出默认 `false`"，避免只断言"加载不报错"。

**修复后的验收标准**

- 存在一条覆盖写入终点的断言（经 patch → 落盘 → 重新加载）。
- 变异：保留白名单但让键名不匹配 serde（或直接丢弃该键）⇒ 至少一条测试转红。

## 三、待确认风险与未验证项

**待确认风险（均非已确认缺陷，不单独阻断，但建议在实现前落结论）**

- **R-1 零重叠退化分支以 `expect` 结束**：`select_monitor_by_overlap` 的兜底为 `.expect("Monitors list must not be empty")`（方案 `:154-156`），与 `dock.rs:1132-1149` 既有的 `Option` 退化链（`select_work_area` 返回 `None`、`work_area_for_point` 空列表提前返回 `None`，`dock.rs:1156-1160`）不一致；若 `monitors` 为空，拖拽松手路径将 panic 而非降级。**怀疑依据**：签名改为非 `Option` 后，函数在"无任何显示器"这一输入上无合法返回值；round 1 的验收口径明确写了"结果 `Ok`（不 panic）"。**缺少的证据**：`available_monitors()` 返回空 vec 的可达性（需要 0 显示器会话，本机无法构造）。**建议**：实现时改回 `Option`（或空列表直接 `return`），并在单测中显式喂入空列表断言不 panic。
- **R-2 恰好 50/50 的归属由枚举顺序决定**：方案 `:147-150` 用严格 `area > max_area` 选优，矩阵第 4 行（`:120`）写"<=50% 留在原屏 A"。**怀疑依据**：独立脚本按伪代码复现 —— 窗口恰好横跨接缝各半时，`monitors = [A,B]` 判归 A、`monitors = [B,A]` 判归 B（`available_monitors()` 顺序不保证），即"留在原屏"这一语义在 50/50 上不成立。**缺少的证据**：实现是否会以 `fallback_index`（原宿主）做 tie-break。**建议**：实现时以 `fallback_index` 破平（或把判据写成显式的"比较原宿主与新最大面积屏"），并在 §7.2.2 增一条"恰 50/50 ⇒ 归属原宿主"的用例。
- **R-3 T-1 的高度余量**：方案已按 round 1 建议锁定 `SETTINGS_DEFAULT_HEIGHT = 620.0`（`:273-276`）。按其自身核算 `620 − (p-5 40 + Header ≈45 + Footer ≈60) ≈ 475px`，对自估的 470px 内容仅余约 5px，并不构成 §5.2 所称的"充分的安全余量"；round 1 建议的 100/150/200% DPI 截图核对未列入方案验证步骤。属 round 1 已记录的非阻断风险，保留至此（实现后仍需截图确认无垂直滚动条）。

**未验证项（受环境限制）**

- 无 GUI 实机：本机无第二台显示器，无法执行多屏/混合 DPI 的拖拽归属、接缝防误折叠、越界回弹、托盘按钮点击与双击时序等端到端检查。
- 未运行任何门禁（本轮为**纯文档**审查，diff 中无产品代码/测试变更）：`npm test`、`npm run build`、`cargo test --locked`、`cargo check --locked` 均未在本轮复现（§一 引用的 65/46 门禁基线来自 v1.1.3 round 5；方案 §8.3 要求在实现轮次复现）。
- 本轮独立验证仅覆盖模块一宽度公式与模块三归属算法的离线边界（§二 P3-2 的脚本），grace/去抖两项只有代码路径推演，无理机 trace。
- 残余风险：`is_external_boundary`（方案 `:161-196`）与 `detect_edge_multi_monitor`（`:204-233`）为纯函数、可离线单测；`apply_pill` / `clamp_position` 的真实几何与拖拽落盘时序仍只能由实机确认（方案 §7.2.4/§7.2.5 已保留单测口径）。
