The feature is a *collaborative request*: the overlay sends a fixed user message into the
running Codex session. It never terminates a Codex process, never writes a transcript and
never starts an app-server of its own to race the desktop client for session writes.

## 2. Where the plan and the live client disagreed

Three points in the plan did not match the running Codex desktop client. The plan's
behaviour is unchanged; the implementation follows the client.

### 2.1 The tool name lives under `tool`

The plan (§5.5) lists the `tools/call` parameters but not their wire names. The client
validates the request against a closed schema:

```text
arguments, callerSource, callId, namespace, threadId, tool, turnId
```

The tool name is the `tool` parameter; the tool's own arguments go into `arguments`.
An earlier draft used `name`, and the client answered `{"code":-32602,"message":"Invalid
app tool request"}`. `build_request` now emits exactly the seven accepted parameters, and
a test asserts the closed key set so a stray parameter turns the build red.

### 2.2 The session transcripts are compressed

The plan (§5.4) collects `.jsonl` files under `%USERPROFILE%\.codex\sessions`. The
current client writes `rollout-<timestamp>-<uuid>.jsonl.zst`, and the thread UUID sits
*before* the extension chain, not at the very end of the file name. The original rule
therefore found no caller identity at all, and every candidate would have been rejected
before the handshake.

The implementation accepts `.jsonl` and `.jsonl.zst` and peels the extension chain until
the trailing 36 characters form a UUID. Both behaviours have regression tests.

### 2.3 A single call needs its own sub-deadline

The plan (§6.2) requires the whole batch to share one five-second deadline and forbids a
per-read budget that would multiply the wait. A candidate whose pipe accepts the
connection and then never answers would still consume the entire batch, so every later
candidate would be starved. Each individual call therefore carries a two-second
sub-deadline inside the five-second batch deadline. The batch bound is unchanged; only a
stuck combination can no longer monopolise it.

## 3. The live bridge was exercised read-only

On this machine the current Codex desktop client exposes one
`codex-app-tools-<uuid>` pipe and twenty legacy `codex-browser-use-<uuid>` pipes. The
read-only checks that were performed:

1. **Discovery** — the pipe enumeration finds the current client's pipe and rejects the
   unrelated `codex-browser-use\<uuid>` form and every name without a valid UUID suffix.
2. **Caller identity** — 32 recent thread identities were collected from the compressed
   session files; the environment variable is honoured first when it holds a valid UUID.
3. **`tools/list`** — the live client answered with the `codex_app` catalog. The published
   schemas confirm the argument shapes: `list_threads` takes an optional integer `limit`
   between 1 and 50, and `send_message_to_thread` requires `threadId` and `prompt` with an
   optional `hostId`.
4. **`list_threads` handshake** — the framed JSON-RPC `tools/call` was accepted by the live
   client and returned real session data: 41 `chatgpt/idle`, 6 `codex/idle` and 9
   `codex/notLoaded` records. The record shape (`id`, `kind`, `status`, `hostId`) is
   exactly what `parse_active_threads` reads.
5. **No target** — no session was `active` at that moment, so the handshake correctly
   produced an empty target list and no message was sent. The read-only checks never
   injected a message into a session.

The client also rejects a caller identity that does not belong to a known thread with
`{"code":-32000,"message":"Codex app tool request failed"}`. That is treated as a failed
handshake and the next candidate is tried, which is the behaviour the plan requires.

### 3.1 The synthetic `turnId` was traced through the client

The envelope's `turnId` was the largest open risk: the plan's `turnId` names no real turn,
and a client that validates it would reject every delivery while all offline tests still
passed. The installed client (`OpenAI.Codex_26.1013.4894.0`) was read for the answer:

- The request schema requires `turnId` to be a **non-empty string** only — no UUID shape,
  no lookup.
- The envelope's `turnId` is read by exactly two places: the `wait_threads` completion
  matching and a de-duplication key for in-flight calls. `send_message_to_thread` does not
  consult it.
- The send path resolves the target by the **argument's** `threadId` and the optional
  `hostId`; the caller's turn identity is not part of the routing.
- Empirically, the read-only `list_threads` handshake in §3 was accepted by the live
  client *with* the synthetic turn id, through the same envelope.

So the residual risk is small, but a real end-to-end send is still the only way to close
it completely.

## 6. Acceptance layers (plan §14)

- The feature is off by default and the three settings save, migrate and validate.
- Only a fresh successful sample triggers a delivery; a sample without an account
  identity never does.
- The four message cases follow the decision matrix exactly, and the 5-hour case rounds
  the remaining time up so the scheduled task cannot fire early.
- A confirmed delivery is de-duplicated per account, quota window, reset cycle and active
  period; a second quota window in the same period is recorded without interrupting the
  session again.
- A bridge failure never blocks the quota read, the tray, the settings or the exit path.
- The documentation separates "compatibility path exists", "read-only handshake passed"
  and "end-to-end delivery verified".

## 7. Residual risks

| # | Item |
| --- | --- |
| P-1 | The client has no `turnId` in its thread records, so the active period falls back to the synthetic counter. Two real turns that swap between two observations are deliberately not treated as two periods — the plan prefers under-sending to double-interrupting. |
| P-2 | The candidate list crosses every discovered pipe with every recent caller identity, which is 672 combinations on this machine. Failures are fast, so the first usable combination is found well inside the batch deadline, but a machine with many unresponsive pipes would rely on the two-second sub-deadline. |
| P-3 | The ledger is in-memory only. A restart clears it, which is the intended behaviour, but it also means a restart inside a low-quota window can produce a second prompt for the same cycle. |
| P-4 | The `codex-browser-use-*` family is implemented and ordered, but no live legacy client was available here, so that path remains a compatibility path rather than a verified one. |
| P-5 | A 5-hour window reported **without** `resetsAt` has no cycle identity, so its de-duplication key can never expire and the session is paused only once per active period. The plan is genuinely split here: §3.1 excludes data that cannot establish a cycle identity, §4.1 requires the plain `暂停` anyway. The implementation follows §4.1 (send, and never claim a scheduled resume it cannot compute). The impact is bounded — a missing reset time also means a plain pause with no resume timer, so nothing scheduled is missed, and a session that leaves the active list starts a new period and is prompted again. |
| P-6 | The plan's §7 prefers under-sending to double-interrupting, so a session that stays continuously active across two exhaustions of the *same* window is interrupted only once, even when the window still has a reset time. A new reset cycle is announced again; a new *active period* is announced again. |

## 9. Review pass

The first implementation was reviewed before the release gate: once by an independent
reviewer that only read the code, and once by a self-review that mutated the production
logic to prove the tests react. Both passes found real problems; all of them are fixed
here.

### 9.1 The active period was never released (the most serious one)

`handshake` treated "the listing contains no active Codex session" as a **failed
handshake**. The active-period bookkeeping is only refreshed on a successful handshake, so
a client that reported an empty list — which is the normal state between two turns — never
ended the active periods. A session that went idle and came back therefore kept its old
period identity, and the plan's §7 rule ("only after the session was actually observed
leaving the active list may a new active period become eligible again") could never fire:
the session was paused **once per quota cycle, for the lifetime of the process**.

The fix separates the two cases. A confirmed call that reports no active session is an
*observation* rather than a broken bridge: the bridge is reachable, the session list is
empty, and every active period ends there. The observation is recorded, the bridge status
stays `available`, and the next candidate is still tried. A regression test drives three
batches — active, idle, active — and asserts that the returning session is prompted
again.

### 9.2 Two mandatory mutation checks did not turn a test red

The plan's §10.6 asks for specific mutations to be caught by the suite. Two were not:

- **The five-second batch deadline.** The old test delayed *every* call, so the batch was
  cancelled inside the handshake, before any reservation existed, and it measured the
  refresh rather than the batch. The scripted bridge now hangs only the send, the test
  measures the worker's own lifetime, and it asserts that the reservation was made and
  then released. Removing the timeout now turns the test red.
- **The quota-cycle expiry.** `an_expired_quota_cycle_is_dropped` passed for the wrong
  reason: the first `prune` also switched the account, and the account switch empties the
  whole ledger. The test now establishes the account first and proves that the record
  still applies while the cycle runs, so the expiry rule is the only remaining reason.

### 9.3 Blocking file system work under the global lock

`deliver_batch` built the candidate list while holding the app-wide `std::sync::Mutex`.
Building it enumerates the named pipes and walks the session directory, so every other
user of the state waited for ordinary file system work — and a blocking call cannot be
interrupted by the batch deadline. The discovery now runs outside the lock, on the
blocking pool, and the session walk is bounded: it visits the newest names first and stops
as soon as 32 files were collected, so a long session history costs no more than a short
one.

### 9.4 Smaller corrections

| Area | Change |
| --- | --- |
| Bridge status | The status used to stay `available` after the bridge stopped answering. It now follows the last handshake, and an empty session list counts as an answered bridge rather than a missing one. |
| Duplicate listing records | A session reported twice, once with and once without a `hostId`, is one session. The record that carries the host id wins, because the client needs it to route the message. |
| Reset distance | A reset further away than six hours is not a 5-hour window; the message falls back to the plain pause instead of asking Codex to wait for days. The plan sets no cap, so this is an implementation decision. |
| Arithmetic | The remaining time is computed with `checked_sub`, so a malformed reset time cannot overflow into a plausible looking duration. |
| Listing shape | The observed live listing shape is pinned by a test, and the parser tolerates one extra layer of JSON encoding instead of silently emptying the target list. |
| Dead state | The `present` flag of the period bookkeeping was always `true`; the branch that read it could never run. It was removed. |
| Test timing | The waiting helper returned as soon as the *handshake* was recorded while the assertions expected the *send*. It now waits for the delivery it asserts on. |

### 9.5 Findings that were not defects

Two reported findings were checked against the code and the plan and did not reproduce:

- A session listed with two host ids is sent to **once**, not twice; the delivery-level
  de-duplication collapses the two records. The parse level keeps the plan's
  `(hostId, id)` key, as §5.5 requires.
- The cycle-less key of a missing `resetsAt` is real, but it is a documented residual risk
  (P-5) rather than a defect, and it is now covered by a regression test that pins the
  behaviour.
