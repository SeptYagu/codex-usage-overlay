The feature is a *collaborative request*: the overlay sends a fixed user message into the
running Codex session. It never terminates a Codex process, never writes a transcript and
never starts an app-server of its own to race the desktop client for session writes.

## 2. Where the plan and the live client disagreed

Three points in the plan did not match the running Codex desktop client. The plan's
behaviour is unchanged; the implementation follows the client.

### 2.1 The tool name lives under `tool`

The plan (§5.5) lists the `tools/call` parameters but not their wire names. The client
validates the request against a closed schema:

```text
arguments, callerSource, callId, namespace, threadId, tool, turnId
```

The tool name is the `tool` parameter; the tool's own arguments go into `arguments`.
An earlier draft used `name`, and the client answered `{"code":-32602,"message":"Invalid
app tool request"}`. `build_request` now emits exactly the seven accepted parameters, and
a test asserts the closed key set so a stray parameter turns the build red.

### 2.2 The session transcripts are compressed

The plan (§5.4) collects `.jsonl` files under `%USERPROFILE%\.codex\sessions`. The
current client writes `rollout-<timestamp>-<uuid>.jsonl.zst`, and the thread UUID sits
*before* the extension chain, not at the very end of the file name. The original rule
therefore found no caller identity at all, and every candidate would have been rejected
before the handshake.

The implementation accepts `.jsonl` and `.jsonl.zst` and peels the extension chain until
the trailing 36 characters form a UUID. Both behaviours have regression tests.

### 2.3 A single call needs its own sub-deadline

The plan (§6.2) requires the whole batch to share one five-second deadline and forbids a
per-read budget that would multiply the wait. A candidate whose pipe accepts the
connection and then never answers would still consume the entire batch, so every later
candidate would be starved. Each individual call therefore carries a two-second
sub-deadline inside the five-second batch deadline. The batch bound is unchanged; only a
stuck combination can no longer monopolise it.

## 3. The live bridge was exercised read-only

On this machine the current Codex desktop client exposes one
`codex-app-tools-<uuid>` pipe and twenty legacy `codex-browser-use-<uuid>` pipes. The
read-only checks that were performed:

1. **Discovery** — the pipe enumeration finds the current client's pipe and rejects the
   unrelated `codex-browser-use\<uuid>` form and every name without a valid UUID suffix.
2. **Caller identity** — 32 recent thread identities were collected from the compressed
   session files; the environment variable is honoured first when it holds a valid UUID.
3. **`tools/list`** — the live client answered with the `codex_app` catalog. The published
   schemas confirm the argument shapes: `list_threads` takes an optional integer `limit`
   between 1 and 50, and `send_message_to_thread` requires `threadId` and `prompt` with an
   optional `hostId`.
4. **`list_threads` handshake** — the framed JSON-RPC `tools/call` was accepted by the live
   client and returned real session data: 41 `chatgpt/idle`, 6 `codex/idle` and 9
   `codex/notLoaded` records. The record shape (`id`, `kind`, `status`, `hostId`) is
   exactly what `parse_active_threads` reads.
5. **No target** — no session was `active` at that moment, so the handshake correctly
   produced an empty target list and no message was sent. The read-only checks never
   injected a message into a session.

The client also rejects a caller identity that does not belong to a known thread with
`{"code":-32000,"message":"Codex app tool request failed"}`. That is treated as a failed
handshake and the next candidate is tried, which is the behaviour the plan requires.

## 5. What is *not* verified

| Layer | State |
| --- | --- |
| Code path implemented | **yes** |
| Automated tests pass | **yes** |
| Read-only handshake against the live client | **yes** |
| A real `send_message_to_thread` delivery | **no** — no Codex session was active on this machine, and injecting a message into a real session was not performed |
| The one-time task that sends `继续` two minutes after the reset | **no** — it is created by Codex from the scheduled message, and it was not observed end to end |
| The signed install package | **no** — packaging, signing and publication are not part of this change |

The distinction matters: the bridge speaks the live protocol, but the delivery and the
scheduled resume have only been exercised against a protocol simulator.

## 6. Acceptance layers (plan §14)

- The feature is off by default and the three settings save, migrate and validate.
- Only a fresh successful sample triggers a delivery; a sample without an account
  identity never does.
- The four message cases follow the decision matrix exactly, and the 5-hour case rounds
  the remaining time up so the scheduled task cannot fire early.
- A confirmed delivery is de-duplicated per account, quota window, reset cycle and active
  period; a second quota window in the same period is recorded without interrupting the
  session again.
- A bridge failure never blocks the quota read, the tray, the settings or the exit path.
- The documentation separates "compatibility path exists", "read-only handshake passed"
  and "end-to-end delivery verified".

## 7. Residual risks

| # | Item |
| --- | --- |
| P-1 | The client has no `turnId` in its thread records, so the active period falls back to the synthetic counter. Two real turns that swap between two observations are deliberately not treated as two periods — the plan prefers under-sending to double-interrupting. |
| P-2 | The candidate list crosses every discovered pipe with every recent caller identity, which is 672 combinations on this machine. Failures are fast, so the first usable combination is found well inside the batch deadline, but a machine with many unresponsive pipes would rely on the two-second sub-deadline. |
| P-3 | The ledger is in-memory only. A restart clears it, which is the intended behaviour, but it also means a restart inside a low-quota window can produce a second prompt for the same cycle. |
| P-4 | The `codex-browser-use-*` family is implemented and ordered, but no live legacy client was available here, so that path remains a compatibility path rather than a verified one. |
